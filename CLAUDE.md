# Правила работы над проектом

Этот файл — источник правды о том, откуда берутся задачи, как мы над ними работаем
и по какому воркфлоу код доезжает до прода. Читается агентом автоматически в начале
каждой сессии. Если реальный процесс разошёлся с этим файлом — правим файл, а не
работаем «как получится».

---

## 1. Откуда берём таски

- Единственный источник задач — **GitHub Project этого репозитория** (доска с issue).
- Работа начинается только с issue, привязанного к Project. Нет issue — нет работы:
  сначала заводим issue, потом кодим.
- Issue = одна задача. Внутри задачи работа делится на фазы (см. §4), фазы issue не плодят.
- Порядок разбора — по колонкам доски и приоритету. Агент не выбирает задачу сам:
  задачу называет человек (по номеру issue) или берётся верхняя в очереди `Ready`.
- Статус задачи на доске обновляется по мере движения: `Todo → In progress → In review → Done`.

## 2. Роли

- **Человек** держит суждение: скоуп, инварианты, доменные решения, финальное ревью и мерж.
- **ИИ** делает механику: чтение кода, сбор контекста, спека, реализация, прогон, механическое ревью.

Правило: делегируем печать, а не мышление. И обратное — человек не тратит время на то,
что проверяется машинально.

## 3. Ветки

- `production` — прод-ветка, в неё уезжает готовый результат. Дефолтная ветка репозитория.
- `feature/<issue>-<slug>` или `fix/<issue>-<slug>` — **базовая ветка задачи**,
  создаётся от `production`. Живёт, пока задача не закрыта целиком.
- `feature/<issue>-<slug>/phase-<n>-<slug>` — ветка одной фазы, создаётся от базовой
  ветки задачи. PR открывается **в базовую ветку задачи**, не в `production`.
- Когда все фазы смержены в базовую ветку задачи — открывается финальный PR
  `feature/<issue>-<slug> → production`.

Прямые коммиты в `production` запрещены. Всё через PR.

## 4. Воркфлоу

### Фаза 0 — Сбор контекста (обязательно)

Перед любым продумыванием человек должен понимать, как работает проект.
ИИ читает код и возвращает карту:

- где живёт затрагиваемый механизм, кто его вызывает, его публичный контракт (входы/выходы);
- побочные эффекты и зависимости (БД, очереди, вебхуки, внешние сервисы);
- для рефакторинга — примеры целевого паттерна, уже существующие в кодовой базе.

«Я не знаю контекста» — это сигнал запустить фазу 0, а не начать писать спеку.
Спека, написанная без контекста, — это угадывание.

### Фаза 1 — Архитектура и дизайн

Три артефакта:

- **Скоуп.** Ценность — в разделе «вне скоупа». In / Out / Допущения.
  Самопроверка: могу назвать 2–3 вещи, которые сознательно не трогаем? Если нет — дизайн не готов.
- **Именованные инварианты.** Что обязано оставаться истинным на любом пути кода.
  Инвариант обязан быть проверяемым (assert / ограничение в БД / тест) и иметь ИМЯ —
  имена уходят в чек-лист ревью. Для рефакторинга главный инвариант — `BEHAVIOR_PRESERVED`.
- **Критерии приёмки.** Given / When / Then, каждый однозначно pass/fail.
  Крайние случаи живут здесь, а не всплывают на ручном ревью.

Отдельно продумываем конкурентность: read-modify-write по общей строке, идемпотентность
при повторной доставке события, зависимость от in-memory состояния, устойчивость переходов
состояний к нарушенному порядку событий.

### Фаза 2 — Спека

Фазы 0–1 записываются в файл `docs/specs/<issue>-<slug>.md` и передаются исполнителю
как контекст. Делегирование звучит как «вот скоуп, вот инварианты, вот определение готовности»,
а не «почини это».

```
## Задача
<одно предложение>

## Скоуп
In: ...
Out: ...
Допущения: ...

## Инварианты
- INVARIANT_NAME: <проверяемое утверждение>

## Критерии приёмки
- [ ] Given ... When ... Then ...
- [ ] <крайний случай>
- [ ] Идемпотентность: <поведение при повторе>

## Фазы
- [ ] Фаза 1: <что> — PR в базовую ветку задачи
- [ ] Фаза 2: ...
```

### Фаза 3 — Разбиение на фазы

Выполнение задачи делится на **логически независимые друг от друга** фазы. Критерий фазы:

- её можно смержить в базовую ветку задачи отдельно и ничего не сломается;
- её можно отревьюить за один заход, не держа в голове остальные фазы;
- у неё есть собственные критерии приёмки — подмножество общих.

Каждая фаза = один PR в базовую ветку задачи.

### Фаза 4 — Реализация

ИИ пишет код по спеке: скоуп + инварианты + критерии приёмки. Одна фаза — одна ветка — один PR.

### Фаза 5 — Прогон (до ревью, не после)

Перед тем как PR уйдёт на ревью человеку, ИИ **сам прогоняет фичу вживую**:

- **Бекенд** — `curl` по реальным ручкам: happy path, ошибочный ввод, повтор запроса
  (идемпотентность). В PR прикладываются команды и ответы.
- **Фронтенд** — поднимается дев-сервер, сценарий проходится в браузере. В PR
  прикладываются скриншоты ключевых состояний.

PR без доказательства прогона на ревью не идёт.

### Фаза 6 — Механическое ревью (ИИ)

ИИ ревьюит прескриптивно, по списку, а не «читает весь диф»:

- самодокументируемые имена;
- одна функция — одно действие;
- читаемость;
- кандидаты на дублирование (сигнал нарушения SSOT);
- лишние или неуместные паттерны (ИИ склонен переприменять паттерны);
- именованные инварианты — соблюдены ли они в дифе.

### Фаза 7 — Ревью человеком и мерж

Человек смотрит только то, что требует доменного знания и понимания намерения,
начиная с высокорисковых зон:

- SSOT: дублирование — это баг рассинхрона или сознательная копия?
- Паттерны: нужен ли паттерн вообще и тот ли он?
- Скоуп и инварианты реально удержаны.
- Крайние случаи из спеки покрыты (подтвердить, а не искать заново).

Разделение: **ИИ ловит механическое, человек решает семантическое.**
Личное правило: не мержить код, который не можешь объяснить вслух.

Правки после ревью делает ИИ, получив на вход конкретные замечания.

### Фаза 8 — Закрытие задачи

Когда все фазы смержены в базовую ветку задачи — открывается PR в `production`.
После мержа issue закрывается, задача на доске уходит в `Done`.

## 5. Требования к PR

- Заголовок: `[<issue>] Фаза <n>: <что сделано>`.
- В теле: ссылка на issue, ссылка на спеку, какие критерии приёмки закрывает,
  доказательство прогона (curl / скриншоты), что осталось на следующие фазы.
- Целевая ветка: базовая ветка задачи (кроме финального PR в `production`).
- PR не открывается, пока не пройдены фаза 5 (прогон) и фаза 6 (механическое ревью).

## 6. Где путаница обычно означает пропущенную фазу

- «Я просто гадаю» на этапе спеки → пропущена фаза 0.
- «Ревью — это очень много работы» → ревью не таргетированное; вернуться и назвать
  инварианты и зоны риска (фазы 1 и 6).
- Крайний случай найден на ручном ревью → это должно было быть критерием приёмки (фаза 1).
- Фазу нельзя смержить отдельно → это не фаза, разбиение сделано неправильно (фаза 3).

## 7. Соглашения по фронтенду

### Мемоизация

Ручную мемоизацию не пишем: ни `useCallback`, ни `useMemo`, ни `React.memo`.
Этим занимается **React Compiler** — он включён в `vite.config.ts`
(`react({ compiler: true })`, работает через `oxc-transform-react`) и применяется
и к сборке, и к дев-серверу, и к прогону тестов.

React 19 сам по себе не мемоизирует — мемоизацию даёт именно компилятор. Проверить,
что он действительно работает, можно по трансформированному модулю: в нём появляется
`const $ = _c(N)` и импорт `react/compiler-runtime`.

```bash
npm run dev
curl -s http://127.0.0.1:5173/src/ui/app/App.tsx | head -20   # ищем _c( и compiler-runtime
```

Следствия, о которых нужно помнить:

- **Компилятор мемоизирует только то, что может доказать.** Он отказывается от
  оптимизации функции, если та нарушает правила React; такие места ловит ESLint —
  в `recommended-latest` из `eslint-plugin-react-hooks` включены правила компилятора
  (`purity`, `immutability`, `set-state-in-render`, `preserve-manual-memoization`
  и другие). Красный линт здесь означает «компилятор не смог», а не «стилистика».
- **Ручная мемоизация не удаляется молча.** Правило `preserve-manual-memoization`
  требует, чтобы уже написанные `useMemo`/`useCallback` оставались корректными.
  Поэтому новые не добавляем, а старые убираем осознанно.
- Сеттер из `useState` и `dispatch` из `useReducer` стабильны сами по себе —
  их не оборачиваем в любом случае.

Если перерисовки всё же станут заметны на реальном объёме — сначала замер, потом
точечное решение, а не обёртки «на всякий случай».

### Стили

- **SCSS-модули.** Компонент импортирует свой `*.module.scss`, лежащий рядом:
  `App.tsx` → `App.module.scss`. Имена классов в модуле — `camelCase`
  (`styles.tabActive`), потому что они читаются из JS.
- **Глобальные стили — только `src/styles/global.scss`** (`:root`, `body`).
  Всё остальное — модули: класс, объявленный в модуле, не может протечь в чужой компонент.
- **Сырые значения живут в `src/styles/_tokens.scss`.** Цвет, отступ, размер шрифта
  в модуле — это токен, а не литерал.
- **Общие куски оформления — миксины в `src/shared/styles/`**, а не копия правил
  в двух модулях (`@use`, затем `@include`).
