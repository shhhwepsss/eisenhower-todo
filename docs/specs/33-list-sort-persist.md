# Фаза 8: Сохранение выбранной сортировки списка

**Issue:** [#33](https://github.com/shhhwepsss/eisenhower-todo/issues/33)  
**Зависит от:** Фаза 7 (вкладка список)  
**Архитектурные разделы:** [docs/specs/4-architecture.md](./4-architecture.md) §2, §8, §9

## Задача

Последняя фаза MVP: персист выбранной сортировки списка в `localStorage` через `SettingsRepository`. Выбор пользователя на сортировку переживает закрытие и открытие приложения.

## Скоуп

**In:**

- Персист `ui.listSort` в отдельный ключ `eisenhower-todo:ui` со схемой версионирования (спека §3).
- Значение по умолчанию — `created` (сортировка по дате создания, дефолт из фазы 7).
- Если в хранилище лежит неизвестное значение сортировки (ошибка пользователя, баг, синхронизация с другой версией приложения), приложение стартует с дефолтом `created` и пишет об этом в лог (не роняет приложение).
- Выбор сортировки пишется в хранилище немедленно при смене — нет кнопки «применить», нет задержки.

**Out:**

- Перемещение других настроек интерфейса в UI Settings (спека §2, §8): в MVP только `listSort`, других нет.
- Синхронизация вкладок браузера: вторая вкладка может разойтись (PRD §6).
- Миграция данных между версиями UI Settings (версия всегда 1 для фазы 8).

## Инварианты

**`DERIVED_ORDER_IS_NOT_STORED`** (спека §2, §8, §9) — смена сортировки списка не пишет в `rank` задач и не сдвигает их `updatedAt`. Порядок пять раз: загрузили со статусом `'ready'`, первый раз открыли список (дефолт `created`), переключились на алфавит, закрыли вкладку, открыли снова. Во всех случаях `rank` одной и той же задачи остался неизменен, `updatedAt` не сдвинулся, если только не было редактирования самой задачи. Проверяется: сравнить объект задачи в памяти до/после смены сортировки.

**`REDUCER_IS_PURE`** (спека §5, §9) — редьюсер получает `listSort` как часть action payload, а не читает его из интерфейса или времени. Action `{ type: 'list-sort/selected', key: ListSortKey }` — это явное заявление о выборе; редьюсер применяет его безусловно и можно его переигрывать (для тестов, логов, повторного применения).

**`STATE_ACCESS_VIA_HOOKS`** (спека §5, §9) — компонент вкладки список получает текущее значение сортировки и функцию её смены через хук `useListSort()`, который возвращает `{ listSort, selectListSort }`. Хук читает из стора, хранилище и стор разделены линией (спека §4).

**`SCHEMA_VERSION_IS_EXPLICIT`** (спека §3, §9) — значение в хранилище имеет форму `{ version: 1, listSort: 'created' }`. Если ключ отсутствует (первый запуск), приложение начинает с дефолта. Если `version` больше известной или не целое число — приложение не ломается, а логирует ошибку и кладёт на диск `{ version: 1, listSort: 'created' }` (выбор: перезаписать или оставить полтави исходные данные — нужно проверить в коде).

## Критерии приёмки

- [ ] **GIVEN** пустой список с дефолтной сортировкой по дате **WHEN** выбрана алфавитная сортировка **THEN** в `localStorage` ключ `eisenhower-todo:ui` содержит `{ version: 1, listSort: 'alphabet' }`.
- [ ] **GIVEN** было выбрано `'quadrant'` **WHEN** страница закрыта и открыта снова **THEN** значение в списке восстановилось на `'quadrant'`, первый кадр (загрузчик) показал эту сортировку, хранилище готово.
- [ ] **GIVEN** в хранилище `{ version: 1, listSort: 'unknown_sort_key' }` **WHEN** приложение стартует **THEN** в консоли сообщение об ошибке; на экране дефолтная сортировка `created`; логируется UUID задачи или другой контекст для отладки.
- [ ] **GIVEN** в хранилище `{ version: 2, listSort: 'created' }` (версия из будущего) **WHEN** приложение стартует **THEN** в консоли предупреждение; приложение не ломается; используется дефолт.
- [ ] **GIVEN** выбрана сортировка и задача отредактирована (описание дополнено) **WHEN** редактор сохранил **THEN** сортировка на месте (не сбросилась), `updatedAt` задачи сдвинулся, но `listSort` в UI Settings не переписан без причины.
- [ ] **GIVEN** три задачи в списке, выбрана алфавитная сортировка **WHEN** первая задача удалена **THEN** порядок оставшихся двух не изменился, алфавитная сортировка по-прежнему активна (выбор сохранилась).
- [ ] Ключ `eisenhower-todo:ui` пишется только через `SettingsRepository.save()`, не напрямую (`localStorage.setItem`). Проверяется ревью кода.
- [ ] `lint`, `build`, `test` проходят.
- [ ] Прогон в браузере: выбрать сортировку, перезагрузить (DevTools → Clear Storage → Reload / или просто Close+Open в приватном окне для чистого состояния), скриншот сортировки сохранился.

## Крайние случаи

| Случай | Поведение |
|---|---|
| Пользователь быстро переключает сортировку (10 раз подряд) | Каждый выбор пишет в `localStorage` синхронно. Последний выбор сохраняется. Это допустимо для локального хранилища (не сетевое, нет лага) |
| `localStorage` недоступен при записи, но был доступен при чтении | Нужно обработать ошибку в `SettingsRepository.save()`. При `error` статусе писать нельзя, поэтому задача не попадёт на диск (спека §3, §5). Остаётся в памяти; пользователь видит выбор, но при перезагрузке сбросит |
| Ключ `eisenhower-todo:ui` повреждён (JSON не парсится) | Не парсится — приложение стартует с дефолтом и перезаписывает ключ правильным значением. Это предусмотрено спекой §3 для задач (`eisenhower-todo:tasks`). Для настроек — то же самое |
| Версия снапшота целое число, но не `1` (скажем, `0`) | `version` неизвестна — не больше и не меньше, а просто не в списке обработанных. Логировать; использовать дефолт |
| Пользователь закрывает приложение прямо во время записи сортировки | `setItem` на `localStorage` — синхронная операция, уже завершилась или полностью откатилась. Частичная запись исключена (спека решение 6 §12: состояние либо записано, либо нет). Однако вторая вкладка в соседнем окне может разойтись — это в рамках PRD §6 |
| У приложения есть два места, где пишется `ui.listSort` (в компоненте и в хуке) | Архитектура требует одну точку записи — редьюсер. Всё остальное читает из стора через хуки. Ревью кода должно найти дублирование |
