# #57 — CI: lint, build и test на каждый PR

## Задача

Гонять корневые `npm run lint`, `npm run build` и `npm test` в GitHub Actions на каждый PR
и не давать мержить красный PR в `production`.

## Прототип

Не требуется: пользователь ничего не видит.

## Решения

Приняты 2026-10-03 (фаза 0 — по коду репозитория).

- **Зачем.** Превью Netlify выключены (#50, `netlify.toml`), а прод собирается на каждый
  мерж в `production`. До мержа PR больше ничего не проверяет: красный lint, сломанная
  сборка или упавший тест уезжают прямо на прод.
- **Один workflow — `.github/workflows/ci.yml`, одна джоба `check`.** Триггеры:
  `pull_request` в любую ветку (PR фаз идут в базовую ветку задачи, не только в
  `production`, `CLAUDE.md` §3) и `push` в `production` — результат мержа тоже
  проверяется, а не только голова PR.
- **Node 22, зафиксирован в workflow.** `.nvmrc` и `engines` в репозитории нет. Нижнюю
  границу задаёт тулчейн из lockfile: Vite 8 и Rolldown — `^20.19.0 || >=22.12.0`,
  ESLint 10 и jsdom — `^20.19.0 || ^22.13.0 || >=24`. `node-version: 22` берёт последний
  22.x, это выше обеих границ; на 22 гонялся и спайк функции в #50. `.nvmrc` не
  заводится: его читает и сборка Netlify, а менять Node прода — не скоуп этой задачи.
- **`actions/checkout@v5` и `actions/setup-node@v5`.** Версии v4 работают на Node 20,
  который GitHub объявил устаревшим для экшенов: первый прогон на v4 дал предупреждение.
  v5 работают на Node 24. Node проекта задаёт `node-version`, а не версия экшена.
- **`npm ci`, а не `npm install`.** Ставится ровно то, что в `package-lock.json`, и
  расхождение lockfile с `package.json` роняет установку, а не тихо чинится.
- **Кеш — только npm** (`setup-node`, `cache: npm`, ключ — хеш lockfile).
  Кешируется загрузочный кеш npm, `node_modules` ставится заново.
- **Lint, build и test — отдельными шагами**, в порядке от дешёвого к дорогому. Упавший
  шаг называет стадию прямо в списке проверок, а не в глубине общего лога.
- **`concurrency`: новый пуш в PR отменяет устаревший прогон** того же PR. Пуши в
  `production` не отменяются — у каждого мержа свой результат.
- **`permissions: contents: read`** — workflow только читает код; токен не может ни
  писать в репозиторий, ни комментировать.
- **Обязательная проверка — настройка репозитория, её включает человек** (см. «Ручной
  шаг»). Workflow без неё лишь сообщает о красном PR, но мерж не запрещает.

### Ручной шаг (человек)

Включается после того, как джоба `check` хотя бы раз отработала — до этого GitHub не
предлагает её в списке проверок.

Вариант через ruleset (Settings → Rules → Rulesets):

1. **New ruleset → New branch ruleset**, имя — `production`, Enforcement status — **Active**.
2. **Target branches → Add target → Include default branch** (или по имени `production`).
3. Включить **Require status checks to pass**, **Add checks** → `check` (источник —
   GitHub Actions). По желанию — **Require branches to be up to date before merging**.
4. Включить **Block force pushes**; **Require a pull request before merging** —
   прямые коммиты в `production` запрещены (`CLAUDE.md` §3).
5. **Create**.

Вариант через классическую защиту (Settings → Branches → Add branch protection rule):
Branch name pattern `production` → **Require a pull request before merging** →
**Require status checks to pass before merging** → найти и добавить `check` → **Create**.

## Скоуп

**In**

- `.github/workflows/ci.yml`: checkout, Node 22 с кешем npm, `npm ci`, `npm run lint`,
  `npm run build`, `npm test`.
- Упоминание CI в README, раздел «Команды».
- Инструкция по обязательной проверке на `production` для человека (выше).

**Out**

- Деплой из CI — его делает Netlify при мерже в `production` (#50).
- Покрытие тестами и его отчёты.
- Кеширование сверх кеша npm (`node_modules`, кеш Vite/ESLint/TypeScript).
- Матрица версий Node и ОС: приложение собирается и деплоится в одном окружении.
- `.nvmrc` / `engines`: смена Node для сборки Netlify — отдельное решение.
- Включение защиты ветки — настройка репозитория, делает человек.

**Допущения**

- GitHub Actions включены в репозитории.
- Тесты не ходят в сеть: `FUNCTION_IS_SELF_CONTAINED` собирает функцию и запускает её
  локально в Node.

## Инварианты

- `CI_RUNS_ROOT_SCRIPTS`: CI запускает ровно те корневые скрипты, что и разработчик
  локально (`npm run lint`, `npm run build`, `npm test`), — никаких команд «только для
  CI». Зелёный локальный прогон и зелёный CI проверяют одно и то же. Проверяется
  чтением workflow: каждый шаг после установки — корневой скрипт из `package.json`.
- `CI_USES_LOCKFILE`: зависимости ставятся `npm ci` — проверяется то, что записано в
  `package-lock.json`, а lockfile, разошедшийся с `package.json`, роняет прогон.
- `CI_READ_ONLY`: токен workflow — `contents: read`; CI ничего не пишет в репозиторий
  и не деплоит.

## Критерии приёмки

- [ ] Given открыт PR в любую ветку When пуш в PR Then запускается джоба `check` и
  проходит шаги Install, Lint, Build, Test.
- [ ] Given упал lint, build или test When смотрим проверки PR Then проверка `check`
  красная, а упавший шаг назван по стадии.
- [ ] Given в PR пришёл новый пуш, пока идёт прогон When стартует новый прогон Then
  старый отменяется.
- [ ] Given мерж в `production` Then `check` прогоняется на результате мержа.
- [ ] Given `package-lock.json` разошёлся с `package.json` Then `npm ci` падает и
  проверка красная.
- [ ] Given текущий `production` When CI на PR этой задачи Then `check` зелёная.
- [ ] Given человек включил обязательную проверку When `check` красная Then кнопка мержа
  заблокирована (ручной шаг, проверяет человек).
