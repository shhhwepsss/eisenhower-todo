# Архитектура MVP — Eisenhower Todo

Статус: принята (ревью пройдено 2026-08-28, решения — §12)
Issue: [#4](https://github.com/shhhwepsss/eisenhower-todo/issues/4)
Источник требований: [`docs/PRD.md`](../PRD.md)

Документ отвечает на вопрос «как», PRD отвечает на «что». Кода приложения здесь нет:
только решения, обоснования и разбиение реализации на фазы. Типы записаны как
декларации — это язык описания модели, а не файлы, которые нужно скопировать.

---

## Задача

Зафиксировать модель данных, механизм хранения, границы слоёв, состав приложения
и порядок реализации так, чтобы решения, которые дорого переигрывать задним числом
(представление порядка, форма записи, граница хранилища), были приняты до первой строчки кода.

## Скоуп

**In:**

- Модель данных задачи и её сериализованное представление.
- Представление ручного порядка внутри квадранта.
- Механизм локального хранения, версионирование схемы и миграции.
- Граница между хранилищем и интерфейсом (порт и адаптер).
- Управление состоянием приложения.
- Сборщик, язык, структура папок, библиотека перетаскивания.
- Хранение выбранной сортировки списка.
- Сопоставление каждого инварианта PRD §4 с местом в архитектуре и способом проверки.
- Разбиение реализации на фазы.

**Out:**

- Код приложения. Реализация идёт отдельными issue по фазам из §11.
- Дизайн интерфейса: вёрстка, цвета, расположение элементов, копирайтинг.
- Реализация синхронизации, серверная часть, аккаунты (PRD §6 «не входит»).
  Модель данных синхронизацию не блокирует, но и не реализует.
- Синхронизация между вкладками браузера (PRD §6 сознательно исключает).
- Тестовая пирамида целиком: здесь названы только проверки инвариантов, а не
  полная стратегия тестирования.
- Деплой, CI, хостинг.

**Допущения:**

- Десятки-сотни задач, один пользователь, одно устройство, один открытый таб
  (PRD §6 «Допущения»).
- Современный десктопный браузер: доступны `crypto.randomUUID`, `localStorage`, ES2022.
- Данные помещаются в квоту `localStorage` с запасом на порядок (расчёт в §4).

## 1. Представление ручного порядка внутри квадранта

### Решение

**Дробное индексирование (fractional indexing): у задачи есть поле `rank` — строка,
сравниваемая лексикографически.** Порядок внутри квадранта — сортировка по `(rank, id)`.
Между любыми двумя ключами всегда можно сгенерировать третий; вставка затрагивает
ровно одну запись.

Библиотека: [`fractional-indexing`](https://www.npmjs.com/package/fractional-indexing)
(реализация схемы Figma, ~1 KB, без зависимостей). Своя реализация не нужна:
алгоритм короткий, но ошибка в нём портит данные молча.

Контракт, который используем:

```
generateKeyBetween(a: string | null, b: string | null): string
// a === null → ключ перед b (вставка в начало)
// b === null → ключ после a (вставка в конец)
// оба null → первый ключ списка ("a0")
```

### Почему не порядковый номер

Порядковый номер (`order: 1, 2, 3`) отвергнут по двум причинам из issue #4 и PRD §9:

- **Вставка в середину переписывает хвост.** Перенос задачи с третьей позиции на первую
  меняет `order` у всех задач выше — N записей вместо одной. Это не только лишняя запись:
  каждая тронутая задача получает новый `updatedAt`, и при будущей синхронизации
  перестановка одной задачи выглядит как правка всего квадранта.
- **Независимые перестановки не сливаются.** Два устройства, вставившие свою задачу
  на позицию 2, дают два разных смысла числа `2`. Разрешить это без дополнительной
  информации нечем.

### Почему не связный список (`prevId` / `nextId`)

Вставка тоже локальна (две записи), но структура хрупкая: разрыв или цикл в указателях
делает квадрант невосстановимым, и проверка целостности стоит дороже, чем сортировка
строк. Кроме того, конкурентная вставка двух задач после одного и того же соседа даёт
расходящийся список, а не два соседних элемента.

### Поведение, которое требует issue #4

**Вставка в середину.** Квадрант: `A(rank="a0")`, `B(rank="a1")`, `C(rank="a2")`.
Пользователь бросает `D` между `A` и `B`:

```
rank(D) = generateKeyBetween("a0", "a1") = "a0V"
```

Записывается одна задача — `D`. Ключи `A`, `B`, `C` не тронуты, их `updatedAt` не меняется.
Порядок: `a0 < a0V < a1 < a2` — `A, D, B, C`. Глубина вложения не ограничена: между
`"a0"` и `"a0V"` найдётся `"a0G"`, и так далее. Ключ растёт в длину примерно на символ
за каждую вставку в одну и ту же щель — при десятках-сотнях задач это единицы байт.

**Две независимые перестановки.** Устройство 1 переносит `X` между `A` и `B`,
устройство 2 в это же время переносит `Y` между теми же `A` и `B`. Оба получают ключи
в интервале `("a0", "a1")` — например `"a0V"` у обоих. После слияния обе задачи
оказываются между `A` и `B` (ни одна не потеряна, порядок вокруг них сохранён),
а между собой упорядочены детерминированно тай-брейком по `id`. Результат осмыслен:
он совпадает с одним из двух вариантов, которые пользователь и так считал бы допустимыми.

Это ключевое отличие от порядкового номера: там конфликт неразрешим, здесь он вырождается
в выбор порядка двух соседей.

### Инварианты представления

- **`RANK_IS_QUADRANT_LOCAL`** — `rank` осмыслен только внутри одного квадранта.
  Сравнивать ранги задач из разных квадрантов запрещено; при переносе между квадрантами
  ранг **всегда** генерируется заново относительно соседей в квадранте-приёмнике.
  Проверка: генерация ранга живёт в одной функции домена, принимающей соседей
  по квадранту-приёмнику; юнит-тест на перенос между квадрантами.
- **`RANK_TOTAL_ORDER`** — сортировка внутри квадранта детерминирована при любых данных,
  включая совпадающие ранги: ключ сортировки — пара `(rank, id)`, `id` уникален глобально.
  Проверка: юнит-тест «два одинаковых ранга → стабильный порядок, не зависящий от
  порядка задач во входном массиве».
- **`RANK_IS_OPAQUE`** — UI не интерпретирует и не конструирует `rank`, только передаёт
  соседей в доменную функцию. Проверка: `rank` не встречается в коде вкладок
  (механическое ревью, фаза 6 `CLAUDE.md`).

### Крайние случаи

| Случай | Поведение |
|---|---|
| Квадрант пуст | `generateKeyBetween(null, null)` |
| Бросок в начало | `generateKeyBetween(null, rank(первой))` |
| Бросок в конец, назначение переключателями, возврат из done | `generateKeyBetween(rank(последней), null)` — PRD §3 «Куда встаёт задача» |
| Бросок на собственное место | Перегенерации нет, `updatedAt` не меняется (идемпотентность) |
| Ранги совпали | Тай-брейк по `id` (`RANK_TOTAL_ORDER`), ребалансировка не нужна |
| Ключ вырос до неприличной длины | При сотнях задач недостижимо. Ребалансировка квадранта в MVP не реализуется; если понадобится — это отдельная задача, а не скрытая логика в UI |

## 2. Модель данных

### Задача

```ts
type TaskStatus = 'todo' | 'in_progress' | 'done';

type Task = {
  id: string;           // UUID v4, crypto.randomUUID()
  text: string;         // непустая после trim строка
  urgent: boolean;      // признак срочности
  important: boolean;   // признак важности
  status: TaskStatus;
  rank: string;         // дробный индекс, порядок внутри квадранта
  createdAt: string;    // ISO-8601 UTC, момент создания
  updatedAt: string;    // ISO-8601 UTC, момент последнего изменения
  deletedAt: string | null; // ISO-8601 UTC — надгробие; null у живой задачи
};
```

Обоснование полей — требования PRD §7 «Готовность к синхронизации»:

- **`id: UUID v4`** — глобально уникален без координации. Последовательные номера отпадают
  прямым текстом PRD. `crypto.randomUUID()` есть в целевых браузерах, внешняя библиотека не нужна.
- **`createdAt` / `updatedAt`** — без них конфликт двух правок неразрешим (PRD §7).
  `createdAt` дополнительно работает как ключ сортировки зоны «Входящие» и списка (PRD §3).
  Строка ISO-8601, а не `Date`: сериализуется без потерь, сравнивается лексикографически,
  переживает `JSON.parse` без ручного оживления.
- **`deletedAt`** — удаление как факт, а не молчаливое исчезновение записи (PRD §7).
  Мягкое удаление: запись остаётся в хранилище, из всех выборок исключается.
- **`rank`** — см. §1.
- **`urgent` / `important`** — два независимых булевых признака (PRD §3).

### Квадрант вычисляется, не хранится

```ts
type Quadrant = 'Q1' | 'Q2' | 'Q3' | 'Q4';
type Placement = { zone: 'inbox' } | { zone: 'quadrant'; quadrant: Quadrant };

// Q1 = urgent && important, Q2 = !urgent && important
// Q3 = urgent && !important, Q4 = !urgent && !important
// inbox = !urgent && !important
```

Здесь есть ловушка, которую нужно назвать явно: **`Q4` и «Входящие» — это одна и та же
пара признаков** `(!urgent, !important)`. По PRD §3 задача без признаков попадает
во «Входящие», а не в Q4. Значит, из пары булевых полей квадрант не выводится однозначно:
`Q4` неотличим от «неразобранной».

**Решение: признаки хранятся не как два `boolean`, а как одно поле разбора.**

```ts
type Priority =
  | { assigned: false }                              // «Входящие»
  | { assigned: true; urgent: boolean; important: boolean }; // квадрант
```

Сериализованная форма (плоская, без вложенного объекта — проще для миграций и для будущего
слияния по полям):

```ts
type Task = {
  id: string;
  text: string;
  assigned: boolean;    // разобрана ли задача
  urgent: boolean;      // осмыслен только при assigned === true
  important: boolean;   // осмыслен только при assigned === true
  status: TaskStatus;
  rank: string;
  createdAt: string;
  updatedAt: string;
  deletedAt: string | null;
};
```

- `assigned: false` → зона «Входящие», `urgent`/`important` игнорируются (нормализуются в `false`).
- `assigned: true` → квадрант вычисляется из пары признаков, включая `Q4` при обоих `false`.
- Перетаскивание во «Входящие» ставит `assigned: false` — PRD §3 «снимает оба признака».
- Переключатели у неразобранной задачи ставят `assigned: true` вместе с признаком.
  Снятие последнего признака **не** возвращает задачу во «Входящие»: она уезжает в `Q4`.
  Возврат во «Входящие» — только явным перетаскиванием.

Это единственное место, где архитектура добавляет к PRD различение, которого в тексте
PRD нет явно. Оно вынужденное: без него `MATRIX_PARTITION` не определён — задача
с обоими `false` претендовала бы сразу на две зоны.

**Решение принято на ревью (§12):** асимметрия сознательная. `Q4` — это осознанный выбор
пользователя «разобрал и решил, что не важно и не срочно», а не побочный результат снятия
галочек. Поэтому в `Q4` может попасть только разобранная задача, а вернуть её в неразобранные
можно единственным жестом — перетаскиванием во «Входящие». Отдельного контрола «снять разбор»
в MVP нет.

Терминология: `assigned` — это **«разобрана»**, не «взята в работу». Прогресс по задаче
живёт в независимом поле `status` (`todo` / `in_progress` / `done`). Задача может быть
разобранной и не начатой (`assigned: true`, `status: 'todo'`) — это обычное состояние
задачи в квадранте.

Квадрант при этом остаётся **вычисляемым** значением, как требует issue #4: хранимого поля
`quadrant` нет, `assigned` — это не квадрант, а признак «разобрана».

### Настройки интерфейса

```ts
type ListSortKey = 'created' | 'alphabet' | 'status' | 'quadrant';
type UiSettings = { listSort: ListSortKey };
```

### Инварианты модели

- **`ID_IS_GLOBALLY_UNIQUE`** — `id` генерируется `crypto.randomUUID()` в одном месте
  (фабрика домена), UI его не конструирует. Проверка: юнит-тест фабрики, механическое ревью.
- **`TIMESTAMPS_MONOTONIC_PER_TASK`** — любая мутация задачи проходит через доменную функцию,
  которая ставит `updatedAt`; «тихих» правок нет. Проверка: юнит-тест «каждая мутация меняет
  `updatedAt`», ревью на прямые спреды `{...task, ...}` вне домена.
- **`DELETE_IS_A_TOMBSTONE`** — удаление ставит `deletedAt`, запись не исчезает; все выборки
  фильтруют `deletedAt === null`. Проверка: юнит-тест «удалённая задача отсутствует
  во всех выборках, но присутствует в снапшоте хранилища».
- **`QUADRANT_IS_DERIVED`** — поля `quadrant` в модели нет. Проверка: тип `Task` не содержит
  такого поля (проверяется компилятором), место задачи определяет одна функция `placementOf`.

## 3. Механизм локального хранения

### Решение

**`localStorage`, один ключ на весь документ задач, JSON-снапшот с версией схемы.**

```
eisenhower-todo:tasks  →  { "version": 1, "tasks": [ ...Task ] }
eisenhower-todo:ui     →  { "version": 1, "listSort": "created" }
```

### Обоснование

- **Объём.** PRD §6: десятки-сотни задач. Задача в JSON — порядка 250–300 байт.
  500 задач ≈ 150 KB при квоте ~5 MB. Запас более чем на порядок; удалённые задачи
  накапливаются надгробиями, но при этом объёме это не проблема.
- **Атомарность записи.** Требование из issue #4. `setItem` для одного ключа атомарен:
  снапшот либо записан целиком, либо не записан. Разложить задачи по отдельным ключам —
  значит получить частично записанное состояние при сбое. Один ключ = одна транзакция.
- **Миграции.** Поле `version` + цепочка чистых функций `v1 → v2 → v3`, применяемых при
  чтении. Схема простая ровно потому, что документ один: миграция — это функция над
  массивом, а не обход хранилища.
- **Синхронность.** Чтение при старте синхронно, приложение не имеет состояния «загружаемся».
  При сотнях задач парсинг — доли миллисекунды.

**Почему не IndexedDB.** IndexedDB выигрывает на объёмах, которых в MVP нет, и на частичных
выборках, которые не нужны (всё состояние всё равно держится в памяти). Цена — асинхронный API,
версионирование через `onupgradeneeded`, обработка блокировок. Это сложность без выигрыша.
Решение обратимо: замена адаптера (§4) не трогает ни экраны, ни домен.

### Инварианты хранения

- **`STORAGE_WRITE_IS_ATOMIC`** — состояние пишется одним `setItem` со всем документом.
  Проверка: в адаптере ровно одна точка записи; ревью.
- **`SCHEMA_VERSION_IS_EXPLICIT`** — снапшот без `version` или с неизвестной версией
  не парсится «как получится». Проверка: юнит-тесты чтения снапшотов v1, битого JSON,
  версии из будущего.
- **`STORAGE_FAILURE_IS_VISIBLE`** — исключение при записи (квота, приватный режим)
  не проглатывается: репозиторий отдаёт ошибку, состояние в памяти остаётся консистентным.
  Проверка: юнит-тест с адаптером, бросающим `QuotaExceededError`.

### Крайние случаи

| Случай | Поведение |
|---|---|
| Ключа нет (первый запуск) | Пустой список задач, настройки по умолчанию |
| JSON не парсится | Не затирать молча. Читать как «данные повреждены», показать сообщение; исходная строка не перезаписывается до явного действия пользователя |
| `version` больше известной | Отказ от чтения с сообщением. Открывать новый формат старым кодом — путь к потере данных |
| Квота исчерпана | Ошибка наверх, состояние в памяти не откатывается |
| `localStorage` недоступен | Приложение работает в памяти на текущую сессию, пользователь предупреждён о том, что данные не сохраняются |

## 4. Граница между хранилищем и интерфейсом

### Решение

**Порт и адаптер.** Домен и стор знают интерфейс `TaskRepository`; конкретная реализация
подставляется на входе в приложение.

```ts
interface TaskRepository {
  loadAll(): Promise<Task[]>;      // включая надгробия
  saveAll(tasks: Task[]): Promise<void>;
}

interface SettingsRepository {
  load(): Promise<UiSettings>;
  save(settings: UiSettings): Promise<void>;
}
```

Асинхронный контракт при синхронной реализации — сознательно: `localStorage` синхронен,
серверная или IndexedDB-реализация нет. Обещание в сигнатуре сейчас стоит ноль, а его
отсутствие потом стоит переписывания вызывающих мест.

Гранулярность `saveAll` вместо `save(task)` — прямое следствие `STORAGE_WRITE_IS_ATOMIC`:
единица записи — снапшот. Для серверной реализации это меняется, но меняется **внутри**
адаптера или в новой версии порта — экраны об этом не знают.

### Направление зависимостей

```
   ui/  ──────────► state/ ──────────► domain/
 (экраны)          (стор)            (чистые правила)
                      │
                      ▼
              TaskRepository  ◄── storage/ (localStorage-адаптер)
                   (порт)
```

- `domain/` не зависит ни от чего: чистые типы и функции.
- `state/` зависит от домена и от **интерфейса** репозитория, не от реализации.
- `storage/` реализует интерфейс и не знает ни про React, ни про экраны.
- `ui/` вызывает действия стора и читает селекторы. Импорт из `storage/` в `ui/` запрещён.

### Инвариант

- **`STORAGE_IS_ISOLATED`** — ни один модуль из `ui/` не импортирует `storage/` и не обращается
  к `localStorage`. Проверка: правило ESLint `no-restricted-imports` на границу слоёв
  плюс запрет `localStorage` в `ui/` — это машинная проверка, а не пункт чек-листа.
  Требование PRD §7: замена локального хранилища на серверное не переписывает экраны.

## 5. Управление состоянием

### Решение

**Один стор на `useReducer` + React Context, без внешнего стейт-менеджера.**
Одно дерево состояния, один редьюсер, обе вкладки — только представления над ним.

```
AppState = { tasks: Task[], ui: UiSettings, storage: 'ready' | 'error' }
```

Персист — подписка на изменение стора: после каждого применённого действия репозиторий
получает снапшот. Запись в хранилище — эффект, а не часть редьюсера: редьюсер остаётся
чистой функцией и тестируется без моков.

### Обоснование

`SINGLE_SOURCE_OF_TRUTH` — инвариант, который лучше держать структурой, а не дисциплиной.
Единственный массив `tasks` в одном сторе делает расхождение вкладок **непредставимым**:
вкладки не хранят копий, им нечем разойтись. Внешняя библиотека этого не усиливает —
Redux или Zustand дают ту же гарантию за счёт той же архитектуры плюс зависимость.

Отказ обоснован масштабом: одно приложение, один пользователь, сотни задач, десяток типов
действий. Причины, по которым обычно берут стейт-менеджер, здесь отсутствуют: нет серверного
кеша, нет middleware, нет межмодульных подписок.

### Шов для замены стора

Решение принято на ревью (§12) с условием: замена `useReducer` на внешний стор должна
стоить переписывания одной папки, а не правок в экранах. **Шов проходит по набору хуков,
экспортируемых из `state/`, а не по интерфейсу объекта-стора.**

```ts
// единственная поверхность, которую видит ui/
useInboxTasks(): Task[]
useQuadrantTasks(quadrant: Quadrant): Task[]
useListGroup(group: ListGroup): Task[]
useStorageStatus(): 'ready' | 'error'
useTaskActions(): TaskActions   // { addTask, editText, setStatus, setPriority, moveToZone, deleteTask }
```

`ui/` не импортирует ни редьюсер, ни объект действий, ни сам Context: только эти хуки.
Хуки-чтения намеренно написаны **в форме селекторов** — принимают параметр зоны и отдают
готовый срез. Тогда переезд на `zustand` или `useSyncExternalStore` меняет только тела
хуков внутри `state/`: сигнатуры уже совпадают с формой селектора.

Явный `interface Store` с адаптером-реализацией **сознательно не вводится**, и это не то же
самое, что порт `TaskRepository` из §4. У репозитория вторая реализация ожидается
(IndexedDB, сервер — PRD §7), у стора её не будет никогда: `useReducer` и внешний стор —
альтернативы, а не сосуществующие реализации. Слой без второй реализации — цена без выигрыша.
Хуже того, интерфейс, описанный в терминах `dispatch(action)`, зафиксировал бы ровно ту модель,
от которой уходят при переезде: выигрыш внешнего стора — точечная подписка через селекторы,
а не форма API. Документирующий контракт при этом остаётся бесплатно — именованный тип
`TaskActions` как возвращаемое значение `useTaskActions()`.

**Что могло бы изменить решение:** заметные лишние перерисовки — Context перерисовывает
поддерево целиком на любое изменение. Порог: если это станет заметно на реальном объёме —
отдельная задача с замером, а не «на всякий случай» сейчас. Благодаря шву это будет замена
содержимого `state/`, а не рефакторинг экранов.

### Инварианты состояния

- **`SINGLE_SOURCE_OF_TRUTH`** (PRD §4) — состояние задач существует в одном экземпляре.
  Проверка: в `ui/` нет `useState`, дублирующего поля задачи; ревью + тест «действие,
  выполненное в одном представлении, отражается в выборке другого».
- **`REDUCER_IS_PURE`** — редьюсер не читает время, не генерирует `id` и не пишет в хранилище:
  всё недетерминированное приходит в action payload (`id`, `now`, `rank`).
  Проверка: юнит-тест «один и тот же state + action дают идентичный результат».
  Это же делает тесты инвариантов дешёвыми — без фейковых таймеров и моков.
- **`STATE_ACCESS_VIA_HOOKS`** — ни один модуль из `ui/` не импортирует редьюсер, действия
  или объект Context: доступ к состоянию только через хуки, перечисленные выше.
  Проверка: правило ESLint `no-restricted-imports` — `ui/` может импортировать из `state/`
  только точку входа с хуками, но не `reducer.ts`, `actions.ts`, `store.tsx`. Тот же механизм,
  что удерживает `STORAGE_IS_ISOLATED` (§4), — машинная проверка, а не пункт чек-листа.

## 6. Сборщик, язык, структура проекта

- **Сборщик — Vite.** React без Next.js (PRD §7). Vite — дефолт для SPA: dev-сервер
  на нативных модулях, нулевая конфигурация, встроенная поддержка TS.
- **Язык — TypeScript, `strict: true`.** Модель держится на размеченных объединениях
  (`Priority`, `Placement`, `TaskStatus`): в TS невалидное состояние не компилируется,
  и часть инвариантов проверяет компилятор, а не тест. Для проекта с продуманной моделью
  данных это самая дешёвая проверка из доступных.
- **Тесты — Vitest.** Тот же конфиг, что у Vite; юнит-тесты домена, редьюсера, адаптера
  хранилища и миграций.
- **Линтер — ESLint** с `no-restricted-imports` для границ слоёв: `STORAGE_IS_ISOLATED` (§4)
  и `STATE_ACCESS_VIA_HOOKS` (§5).

### Структура папок

Слоистая, границы совпадают с §4:

```
src/
  domain/      task.ts, placement.ts, ordering.ts, factory.ts   — типы и чистые правила
  storage/     repository.ts (порт), local-storage.ts, migrations.ts
  state/       index.ts (хуки — единственный вход для ui/), store.tsx, reducer.ts,
               actions.ts, selectors.ts
  ui/
    app/       index.ts, App.tsx, app.css, children/, hooks/, helpers/,
               constants/, types/
    list/      вкладка «Список»
    matrix/    вкладка «Матрица»
    task/      общие представления задачи
  shared/      мелкие утилиты без доменного смысла

tests/         зеркало src/: tests/ui/app/App.test.tsx и т.д.
               плюс общие setup.ts и layer-boundaries.test.ts
```

Раскладка внутри слайса (решение ревью фазы 1):

```
src/ui/app/
  index.ts     публичный контракт слайса
  App.tsx      единственный компонент в корне
  app.css
  children/    только разметка, ровно один уровень вложенности
  hooks/       состояние и эффекты слайса
  helpers/     чистые функции слайса
  constants/   константы слайса: tabs.ts (TABS, DEFAULT_TAB) + index.ts
  types/       по файлу на тип: tab-id.ts, tab-item.ts, tabs.ts,
               active-tab.ts + index.ts
```

- `index.ts` — единственный публичный контракт слайса. Всё остальное приватно.
- В корне слайса лежит один `.tsx` — сам компонент слайса. Остальные компоненты
  живут в `children/`.
- **`children/` не содержит логики.** Один уровень вложенности, только представление.
  Если компоненту нужна логика — она переезжает в `hooks/` или `helpers/`, а не
  остаётся рядом с разметкой.
- Тесты живут в зеркальном дереве `tests/`, а не рядом с кодом: `src/` содержит
  только продовый код.

Импорт чужого слайса — только через его `index.ts` по алиасу `@/` (`@/ui/list`).
Инвариант **`SLICE_PUBLIC_API`**: обход `index.ts` (`@/ui/app/tabs`, `@/ui/app/lib/...`,
относительный путь через два уровня вверх) запрещён правилом `no-restricted-imports`
для `src/ui/**`. На `tests/` правило не распространяется: тест на то и тест, чтобы
дотянуться до внутренностей проверяемого модуля.

Полноценный FSD (`entities/features/widgets/pages`) для приложения с одной сущностью
и двумя экранами — лишняя церемония: слоёв больше, чем содержимого. Слоистая структура
даёт ту же изоляцию хранилища при меньшем числе папок. Если сущностей станет больше —
структура вырастет в FSD без переписывания домена.

## 7. Перетаскивание

**Решение: `@dnd-kit` (`@dnd-kit/core` + `@dnd-kit/sortable`).**

Требуются два разных жеста (PRD §3, §6): перенос между зонами (из «Входящих» в квадрант,
между квадрантами, из квадранта во «Входящие») и сортировка внутри квадранта с попаданием
в конкретную позицию. `@dnd-kit/sortable` покрывает оба: даёт индекс вставки, из которого
берутся соседи для генерации ранга.

- **Не HTML5 Drag and Drop API** — нативный API даёт слабый контроль над превью и
  подсветкой зоны, и его поведение расходится между браузерами. Точная позиция вставки
  на нём делается вручную.
- **Не `react-beautiful-dnd`** — библиотека в архивном состоянии, новые версии React
  не поддерживаются.
- **Не своя реализация** — перетаскивание с индексом вставки и автоскроллом это не
  «сто строк на pointer-событиях», а работа, которая уже сделана и оттестирована.

Сенсорный ввод не прорабатывается (PRD §6 «Допущения»), но `@dnd-kit` его поддерживает
из коробки — это не стоит нам ничего.

**Граница:** библиотека живёт только в `ui/matrix`. Результат броска переводится в вызов
доменного действия «перемести задачу в зону Z между соседями A и B» — домен о существовании
`@dnd-kit` не знает. Проверка: импорты `@dnd-kit` вне `ui/` запрещены (ESLint).

## 8. Сохранение выбранной сортировки списка

**Решение: сортировка запоминается между сессиями и хранится отдельным ключом
`eisenhower-todo:ui` как настройка интерфейса, а не рядом с задачами.**

- **Запоминается** — PRD §6 прямо требует: «после перезагрузки всё на месте, включая
  выбранную сортировку списка».
- **Отдельно от задач** — три причины. Это свойство пользователя, а не задачи
  (`DERIVED_ORDER_IS_NOT_STORED`). Смена сортировки не должна касаться документа задач
  и трогать их `updatedAt`. И при будущей синхронизации задачи синхронизируются,
  а настройка вида — устройство-локальная; разделение по ключам делает это решение
  бесплатным, а не миграцией.

Значение по умолчанию — `created` (дата создания). Неизвестное значение в хранилище
заменяется дефолтом, а не роняет приложение.

## 9. Карта инвариантов PRD §4

Каждый инвариант продукта — место в архитектуре, которое его удерживает, и способ проверки.

| Инвариант | Где удерживается | Как проверяется |
|---|---|---|
| `SINGLE_SOURCE_OF_TRUTH` | Один стор, одно дерево состояния (§5). Вкладки — представления, копий не держат | Ревью: в `ui/` нет состояния, дублирующего поля задачи. Тест: действие в одном представлении видно в выборке другого |
| `LIST_IS_COMPLETE` | Селектор списка не фильтрует ничего, кроме `deletedAt !== null` (§2) | Свойство-тест: объединение трёх групп списка = все живые задачи, для произвольного набора |
| `DONE_LEAVES_MATRIX` | Селекторы матрицы (входящие + квадранты) исключают `status === 'done'` | Тест: задача в `done` отсутствует во всех выборках матрицы, включая «Входящие» |
| `MATRIX_PARTITION` | `placementOf(task)` — одна функция, возвращающая размеченное объединение `Placement`; вернуть две зоны невозможно по типу | Компилятор (сумма-тип) + свойство-тест: сумма размеров зон матрицы = число живых не-`done` задач |
| `LIST_PARTITION` | Группа выводится одной функцией `listGroupOf(task)` с сумма-типом `'inbox' \| 'assigned' \| 'done'` | Компилятор + свойство-тест: группы не пересекаются и покрывают всё |
| `MANUAL_PRIORITISATION` | `assigned`/`urgent`/`important` меняют ровно два действия: `setPriority` и `moveToZone`. Ни `createTask`, ни `setStatus` их не касаются | Тест: `createTask` даёт `assigned: false`; `setStatus` в обе стороны не меняет тройку признаков |
| `PRIORITY_SURVIVES_DONE` | То же: `setStatus` не трогает признаки | Тест: `todo → done → todo` сохраняет `assigned/urgent/important`; задача возвращается в тот же квадрант |
| `ORDER_IS_PERSISTENT` | `rank` — поле задачи, попадает в снапшот. Пересчёта рангов в коде нет нигде, кроме явного перемещения (§1) | Тест: сохранить → загрузить → порядок в квадранте совпадает. Ревью: `rank` присваивается только в `ordering.ts` |
| `DERIVED_ORDER_IS_NOT_STORED` | Порядок «Входящих» — сортировка по `createdAt` в селекторе; порядок списка — сортировка по `ui.listSort`. Ни одна из них не пишет в задачу | Тест: смена сортировки списка и попадание задачи во «Входящие» не меняют `rank` и `updatedAt` |

Инварианты, добавленные архитектурой: `RANK_IS_QUADRANT_LOCAL`, `RANK_TOTAL_ORDER`,
`RANK_IS_OPAQUE` (§1); `ID_IS_GLOBALLY_UNIQUE`, `TIMESTAMPS_MONOTONIC_PER_TASK`,
`DELETE_IS_A_TOMBSTONE`, `QUADRANT_IS_DERIVED` (§2); `STORAGE_WRITE_IS_ATOMIC`,
`SCHEMA_VERSION_IS_EXPLICIT`, `STORAGE_FAILURE_IS_VISIBLE` (§3); `STORAGE_IS_ISOLATED` (§4);
`REDUCER_IS_PURE`, `STATE_ACCESS_VIA_HOOKS` (§5).

## 10. Конкурентность

`CLAUDE.md` §4 требует продумать конкурентность отдельно. Для MVP она вырождена, и полезно
зафиксировать почему.

- **Read-modify-write по общей записи.** Внутри приложения мутации последовательны:
  React-события обрабатываются по одному, редьюсер синхронен. Единственный настоящий
  конкурент — вторая вкладка браузера, и PRD §6 её сознательно исключает: две вкладки
  могут разойтись до перезагрузки. Событие `storage` не слушаем — половинчатая
  синхронизация вкладок хуже честного отсутствия.
- **Идемпотентность.** Действия сформулированы как «привести к состоянию», а не «переключить»:
  `setStatus(id, status)`, `setPriority(id, priority)`, `moveToZone(id, zone, between)`.
  Повторное применение того же действия даёт то же состояние. Бросок задачи на её текущее
  место рангов не трогает. `deleteTask` для уже удалённой задачи — no-op, `deletedAt`
  не переписывается.
- **In-memory состояние.** Состояние в памяти — кеш поверх снапшота, восстанавливается
  из хранилища при старте целиком. Данных, живущих только в памяти, нет.
- **Порядок событий.** Модель к нему устойчива: `rank` не зависит от порядка вставок,
  а переходы статусов свободны в обе стороны (PRD §3), поэтому «неправильного» порядка
  переходов не существует. Это то, что делает модель пригодной для синхронизации позже.

## 11. Разбиение реализации на фазы

Критерий фазы (`CLAUDE.md` §4): мержится в базовую ветку задачи отдельно, ничего не ломая;
ревьюится за один заход; имеет собственные критерии приёмки. Каждая фаза — отдельный issue
и отдельный PR.

**Фаза 1 — Каркас проекта.**
Vite + React + TypeScript (`strict`), Vitest, пустая структура папок из §6, приложение
запускается и показывает две пустые вкладки. ESLint с `no-restricted-imports` на **обе**
границы слоёв сразу: `STORAGE_IS_ISOLATED` (§4) и `STATE_ACCESS_VIA_HOOKS` (§5).
Мержится отдельно: рабочий репозиторий без функциональности.
Приёмка: `dev`, `build`, `test`, `lint` проходят; каждое из двух правил границ срабатывает
на заведомо запрещённом импорте.

Обе границы конфигурируются здесь, хотя модулей за ними ещё нет: `no-restricted-imports`
работает по строке импорта и не резолвит модуль, поэтому правило проверяемо до появления
`storage/` и `state/`. Настроить границу до того, как её станет что нарушать, дешевле,
чем чинить нарушения задним числом в фазах 3 и 4.

**Фаза 2 — Доменное ядро.**
Типы `Task`, `Priority`, `Placement`, `TaskStatus`; `placementOf`, `listGroupOf`, фабрика
задачи, генерация и сравнение рангов, чистые функции мутаций. Без React и без хранилища.
Мержится отдельно: код, покрытый тестами, никем ещё не вызываемый.
Приёмка: тесты `MATRIX_PARTITION`, `LIST_PARTITION`, `RANK_TOTAL_ORDER`,
`RANK_IS_QUADRANT_LOCAL`, `ID_IS_GLOBALLY_UNIQUE`, `TIMESTAMPS_MONOTONIC_PER_TASK`,
`QUADRANT_IS_DERIVED`; поведение вставки в середину из §1.

**Фаза 3 — Хранилище.**
Порт `TaskRepository` / `SettingsRepository`, адаптер `localStorage`, версия схемы,
каркас миграций, разбор повреждённых данных.
Мержется отдельно: реализация порта, ещё не подключённая к UI.
Приёмка: `STORAGE_WRITE_IS_ATOMIC`, `SCHEMA_VERSION_IS_EXPLICIT`, `STORAGE_FAILURE_IS_VISIBLE`,
`DELETE_IS_A_TOMBSTONE`; крайние случаи из §3.

**Фаза 4 — Стор и селекторы.**
Редьюсер, действия, Context, персист через репозиторий, хуки-селекторы групп списка
и зон матрицы (§5).
Мержится отдельно: состояние работает и тестируется, экранов ещё нет.
Приёмка: `SINGLE_SOURCE_OF_TRUTH`, `REDUCER_IS_PURE`, `STATE_ACCESS_VIA_HOOKS` (правило
настроено в фазе 1; здесь проверяется, что поверхность хуков из §5 существует и `lint`
проходит на реальном коде), `MANUAL_PRIORITISATION`,
`PRIORITY_SURVIVES_DONE`, `DONE_LEAVES_MATRIX`, `ORDER_IS_PERSISTENT` (сохранить → загрузить),
идемпотентность действий из §10.

**Фаза 5 — Вкладка «Матрица» без перетаскивания.**
Зона «Входящие» рядом с четырьмя квадрантами, порядок входящих по `createdAt`, назначение
квадранта переключателями, скрытие `done`.
Мержится отдельно: матрица работает, разбор идёт переключателями.
Приёмка: `MATRIX_PARTITION`, `DONE_LEAVES_MATRIX`, `DERIVED_ORDER_IS_NOT_STORED`;
сценарии PRD S3, S6, S6a; прогон в браузере (`CLAUDE.md` фаза 5).

**Фаза 6 — Перетаскивание.**
`@dnd-kit`, перенос между зонами, сортировка внутри квадранта с попаданием в позицию,
генерация рангов по соседям.
Мержется отдельно: до неё матрица уже работает переключателями, после — добавляется жест.
Приёмка: сценарии PRD S2, S4; крайние случаи вставки из §1; `RANK_IS_OPAQUE`;
`ORDER_IS_PERSISTENT` после перезагрузки; возврат задачи из квадранта во «Входящие» (§2).

**Фаза 7 — Вкладка «Список».**
Создание, редактирование, удаление задачи, переключение статуса и признаков, три группы,
сортировка внутри групп (без сохранения выбора).
Мержится отдельно: вторая вкладка поверх готового стора, матрицу не трогает.
Приёмка: `LIST_IS_COMPLETE`, `LIST_PARTITION`; сценарии PRD S1, S4a, S5; прогон в браузере
(`CLAUDE.md` фаза 5).

**Фаза 8 — Сохранение выбранной сортировки списка.**
`SettingsRepository`, персист `listSort`, дефолт и разбор неизвестного значения.
Мержится отдельно: маленькая фаза поверх готовой сортировки из фазы 7.
Приёмка: §8; выбор переживает перезагрузку; `DERIVED_ORDER_IS_NOT_STORED` не нарушен.

Зависимости: 1 → 2 → 3 → 4 → {5, 7}, 6 после 5, 8 после 7.
Матрица (5) и список (7) независимы между собой.

**Порядок принят на ревью (§12): матрица раньше списка.** Матрица — ядро продукта, и она же
собирает весь риск архитектуры: `@dnd-kit` и дробное индексирование. Упереться в них лучше
там, где решения ещё дёшево менять.

Следствие, которое нужно назвать явно: между фазами 5 и 6 «Входящие» работают как дверь
в одну сторону. Задача уходит оттуда переключателем, а вернуть её обратно по решению §2
можно только перетаскиванием — то есть не раньше фазы 6. Это допустимое промежуточное
состояние внутри базовой ветки задачи, но фаза 5 не показывается как готовый продукт
и в `production` в таком виде не уезжает.

## 12. Решения, принятые на ревью

Ревью 2026-08-28. Четыре пункта, которые архитектура не имела права решить сама.

**1. Различение `Q4` и «Входящих» через поле `assigned` (§2) — принято.**
Асимметрия сознательная: `Q4` — это результат разбора («не важно и не срочно»), а не
побочный эффект снятия галочек. Поэтому снятие последнего признака оставляет задачу
разобранной и отправляет её в `Q4`; вернуть задачу в неразобранные можно только
перетаскиванием во «Входящие». Отдельного контрола «снять разбор» в MVP нет — вернуться
к этому после MVP. Уточнение терминологии: `assigned` = «разобрана», прогресс по задаче
живёт в независимом `status`.

**2. Отказ от внешнего стейт-менеджера (§5) — принято, с условием по шву.**
`useReducer` + Context, но поверхность для `ui/` — набор хуков в форме селекторов,
а не редьюсер и не Context напрямую. Условие превращено в проверяемый инвариант
`STATE_ACCESS_VIA_HOOKS` (правило ESLint). Явный `interface Store` с адаптером отклонён
как слой без второй реализации — обоснование в §5.

**3. Порядок фаз (§11) — матрица раньше списка.**
Новый порядок: 1 → 2 → 3 → 4 → 5 (матрица) → 6 (перетаскивание) → 7 (список) → 8 (сортировка).
Принятое следствие: между фазами 5 и 6 «Входящие» — дверь в одну сторону (§11).

**4. Ресерч-issue #6, #7, #8 — закрыты как поглощённые этой спекой.**
Решения приняты и обоснованы здесь: стейт-менеджер — §5, механизм хранения — §3,
библиотека перетаскивания — §7. Отдельного ресерча не будет.

### Что осталось за MVP

- Контрол «вернуть задачу во «Входящие»» помимо перетаскивания (см. решение 1).
- Ребалансировка рангов, если ключи вырастут (§1, крайние случаи).
- Синхронизация между вкладками браузера (PRD §6 исключает сознательно).
