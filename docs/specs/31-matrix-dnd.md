# Фаза 6: Перетаскивание задач на вкладке «Матрица»

**Issue:** [#31](https://github.com/shhhwepsss/eisenhower-todo/issues/31)  
**Зависит от:** Фаза 5 (вкладка матрица), Фаза 7 (вкладка список)  
**Архитектурные разделы:** [docs/specs/4-architecture.md](./4-architecture.md) §1, §7, §11

## Задача

Реализовать перетаскивание задач на вкладке «Матрица» через библиотеку `@dnd-kit`. Жест становится единственным способом вернуть задачу из квадранта во «Входящие» (спека решение 3 §12: асимметричный разбор).

Библиотека выбрана архитектурой (§7), ресерча не ведётся. Перетаскивание в списке (фаза 7) не реализуется — его нет по PRD §3.

## Скоуп

**In:**

- Перенос задачи между пятью зонами матрицы: из «Входящих» в квадрант, между квадрантами, из квадранта во «Входящие».
- Сортировка внутри квадранта при приземлении в выбранную позицию — ранг пересчитывается между соседями целевой позиции.
- Сенсоры: мышь (PointerSensor) с порогом активации 4 пикселя для защиты кликов на переключателях; клавиатура (KeyboardSensor) для доступности — возврат во «Входящие» должен работать не только мышью.
- Ранг генерируется по соседям позиции-приёмника, а не по индексу или длине массива — инвариант `RANK_IS_OPAQUE`.
- Соседи всегда из целевого квадранта, никогда не из других квадрантов — инвариант `RANK_IS_QUADRANT_LOCAL`.
- Порядок переживает перезагрузку страницы — инвариант `ORDER_IS_PERSISTENT`.
- Импорты `@dnd-kit` разрешены только в `ui/matrix/`. Ни из `state/`, ни из `domain/`, ни из `storage/` не импортируем библиотеку.

**Out:**

- Перетаскивание в списке (фаза 7) — его нет по PRD §3. Список показывает выборку, сортировку, но не порядок перемещения.
- Перетаскивание внутри зоны «Входящие» — порядок там вычисляется по `createdAt` и за счёт этого всегда консистентен. Переместить входящую задачу внутри входящих — бесполезно, так как она вернётся на место при перезагрузке.
- Сенсорный ввод (touch) — PRD §6 отнесён к выпуску после MVP.
- Анимация расползания элементов при бросе.

## Инварианты

**`RANK_IS_OPAQUE`** (спека §1, §9) — интерфейс между компонентом матрицы и редьюсером использует соседей задачи, а не строки рангов. Действие `moveToZone(taskId, zone, between: Neighbours)` принимает `Neighbours = { before?: Task; after?: Task }`, не `Neighbours = { before?: string; after?: string }`. Ранг вычисляется редьюсером через `generateKeyBetween()`, компонент об этом не знает.

**`RANK_IS_QUADRANT_LOCAL`** (спека §1, §9) — соседи, переданные компонентом, всегда принадлежат целевому квадранту, а не чужому. При бросе в Q2 соседи берутся из Q2, никогда не из Q3. Это упрощает алгоритм и делает его предсказуемым: ранг `between(Q2[i], Q2[i+1])` не может случайно оказаться меньше ранга уже существующей задачи в Q1.

**`ORDER_IS_PERSISTENT`** (спека §1, §9, решение 3 §12) — `rank` попадает в снапшот и переживает перезагрузку вкладки. При старте задачи в квадранте появляются в том же порядке, в котором их поместили перетаскиванием.

**`MANUAL_PRIORITISATION`** (спека §2, §9) — бросок выставляет признаки (`assigned`, `urgent`, `important`) в соответствии с целевым квадрантом. Приложение не вычисляет квадрант задачи само; при бросе во «Входящие» признаки снимаются (задача в `assigned: false`), что соответствует решению 1 §12.

**`STATE_ACCESS_VIA_HOOKS`** (спека §5, §9) — компонент `MatrixTab` вызывает только `useMatrixZones()` (чтение) и `useTaskActions()` (действие `moveToZone`), больше ничего. Импорт из `@/state` ограничен этими хуками.

**`SINGLE_SOURCE_OF_TRUTH`** (спека §5, §9) — перемещение одной задачи в матрице немедленно видно в выборке списка (если список открыт, или при переходе на список после перемещения). Нет локального кеша положения задачи в компоненте — используется лишь редьюсер.

**`RANK_TOTAL_ORDER`** (спека §1, §9) — ранги внутри квадранта образуют полный порядок; лексикографический срав`нение двух рангов даёт консистентный результат с другими сравнениями. Сортировка `(rank, id)` не может дать два разных порядка при двух попытках.

## Критерии приёмки

- [ ] **GIVEN** задача во «Входящих** **WHEN** брошена в Q2 **THEN** у неё выставлены `assigned: true, urgent: false, important: true` и она появляется в Q2 на месте приземления (между указанными соседями).
- [ ] **GIVEN** три задачи в Q1 c рангами `["a0", "a1", "a2"]` **WHEN** нижняя (ранг `"a2"`) брошена между первой и второй **THEN** порядок сортировки `(rank, id)` изменился: новый порядок — `["a0", <new>, "a1"]` или эквивалент, где `new` между `"a0"` и `"a1"` лексикографически.
- [ ] **GIVEN** задача в Q1 **WHEN** брошена во «Входящие** **THEN** у неё выставлены `assigned: false, urgent: false, important: false`.
- [ ] **GIVEN** задача брошена в Q1 точно на свою текущую позицию (идемпотентность) **WHEN** редьюсер обработает бросок **THEN** `rank` остался прежним, `updatedAt` не сдвинут (действие — no-op).
- [ ] **GIVEN** задача переместилась в Q2 **WHEN** страница перезагружена (Ctrl+R) **THEN** она по-прежнему в Q2, на том же месте в квадранте.
- [ ] **GIVEN** задача во «Входящих** **WHEN** перетащена мышью на карточку в Q1 (расстояние < 4px перемещения) **THEN** щелчок на переключателе срочности (который находится на карточке) зарегистрирован, а не интерпретирован как начало перетаскивания.
- [ ] **GIVEN** задача во «Входящих** **WHEN** перетащена с клавиатуры (Space → Arrow → Enter) в Q2 **THEN** она оказывается в Q2, с признаками Q2, `Storage: 'ready'` на момент отпускания.
- [ ] `lint`, `build`, `test` проходят.
- [ ] Прогон в браузере (сценарии PRD S2, S4), скриншоты прикреплены в PR.

## Крайние случаи

| Случай | Поведение |
|---|---|
| Бросок в позицию снаружи квадранта (over-zone не совпадает с drop-target) | `resolveDrop()` возвращает `null`, бросок не применяется — задача возвращается на место |
| Одновременно два броска из двух вкладок браузера | Фаза 6 не синхронизирует вкладки. В сценарии PRD §6 две вкладки могут разойтись до перезагрузки. Последний `setItem` побеждает. Это известное ограничение MVP |
| Ранг переполняется (дробное индексирование не находит место) | Маловероятно при сотнях задач, но возможно при миллионах операций. Решение вне скоупа фазы 6 |
| Сосед задачи удалён (в снапшоте соседа нет, но в компоненте он ещё есть) | Компонент передаёт соседей по `id`. Редьюсер валидирует: если соседа нет в текущем квадранте, считает это race condition и отклоняет бросок или заменяет соседа на `null` (вставить в конец). Это нужно проверить в коде |
| Целевой квадрант пуст (нет соседей) | `generateKeyBetween(null, null)` вернёт первый ранг `"a0"`. Бросок применяется, задача становится первой в пустом квадранте |
| Активный сенсор pointer менее 4px, но пользователь всё равно хотел кликнуть на переключатель | Порог 4px — компромисс. Для контрола нужно тестирование UX, но подразумевается, что 4px достаточно для различия клика и движения |
