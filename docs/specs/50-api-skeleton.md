# #50 — Скелет API на Netlify Functions

## Задача

Поднять `apps/api`: Hono за одной функцией Netlify на том же сайте, что и фронт, со
служебной ручкой и своими правилами кода — без базы и без входа.

## Прототип

Не требуется: пользователь ничего не видит.

## Решения

Приняты человеком 2026-09-23 — 2026-09-28; результаты фазы 0 — 2026-10-02.

- **Хостинг — Netlify, один сайт с фронтом.** Фронт уже собирается в статику
  (`vite build`). Один origin — значит CORS не нужен, а cookie-авторизация (#52) работает
  без обходных путей.
- **Рантайм — Netlify Functions на Node, не Edge Functions.** Обработчик функции принимает
  стандартные `Request`/`Response`
  ([docs.netlify.com/build/functions/api](https://docs.netlify.com/build/functions/api)),
  у Hono `app.fetch` ровно такой сигнатуры — адаптер не нужен. Официальный путь Hono для
  Netlify — Edge Functions
  ([hono.dev/docs/getting-started/netlify](https://hono.dev/docs/getting-started/netlify)),
  но это Deno и импорты `jsr:`, что усложняет npm-пакеты и драйверы базы; выигрыш в
  задержке личному планировщику не нужен.
- **Фреймворк — Hono.** Fastify и NestJS решают ту же задачу; берётся что-то одно.
- **Валидация — zod на обоих слоях**: и входные данные HTTP, и бизнес-правила.
  `class-validator` рядом с zod описывал бы форму `Task` второй раз.
- **Сущности — классы с методами.** Запрет `FunctionExpression` живёт в общей базе
  (`eslint.config.base.js`, правило `no-restricted-syntax`) и в `apps/api` снимается:
  методы класса в ESTree — это `FunctionExpression`, правило их запретило бы. Поэтому
  правило «только стрелочные» (`CLAUDE.md` §8) явно сужается, а не обходится молча.
- **DTO и маппер на каждой границе** — контроллер, use-case, сущность, база.
  `system-architect` советовал обратное (схлопнуть до двух представлений: `Task` уже
  сериализуемая форма, `packages/core/src/types/task.type.ts`), человек отклонил осознанно.
  Цена: новое поле задачи добавляется примерно в семи местах вместо двух; при точно
  типизированных мапперах забытое поле ловит компилятор — это объём работы, а не тихая
  поломка. Соглашение вводится здесь, первые DTO появляются в #46.
- **Что serverless меняет в требованиях:**
  - процесс не живёт между запросами — ни кеш, ни состояние в памяти не держим;
  - файловая система одноразовая — база только внешняя (#51);
  - синхронная функция ограничена 60 секундами
    ([docs.netlify.com/build/functions/configuration](https://docs.netlify.com/build/functions/configuration)).

### Результаты фазы 0 (2026-10-02)

Документация Netlify из окружения агента недоступна (сеть), поэтому ответы получены из
исходников `@netlify/zip-it-and-ship-it@16.2.3` (бандлер функций, которым пользуются и
сборка Netlify, и `netlify dev`) и `@netlify/functions@6.0.2` (типы), а затем проверены
спайком: настоящий бандлер на копии репозитория, запуск собранной функции в Node 22.
Пакеты ставились во временную папку, в проект не попали.

- **Маршрут — `export const config = { path: '/api/*' }` в функции**, не redirect в
  `netlify.toml`. Бандлер читает `config` статически и превращает его в маршрут
  `^/api(?:/(.*))/?$`. Маршрут живёт рядом с кодом, который его обслуживает; `excludedPath`
  есть на случай исключений. Следствие: голый `/api` без слэша в функцию не попадает.
- **`@eisenhower/core` исходниками в функцию не доезжает — сборка зелёная, функция
  падает.** Функция с `export default (req) => Response` — это v2, а v2 бандлер всегда
  собирает через NFT + esbuild с `packages: 'external'`: любой голый импорт, включая
  workspace-пакет, остаётся внешним. В архив попадает `packages/core/package.json`, но не
  `src/*.ts`, и на первом же запросе — `ERR_MODULE_NOT_FOUND: …/core/src/index.ts`.
  Даже доедь файлы, Node не исполнил бы ни `.ts` из `node_modules`, ни импорты core без
  расширений (`'./constants'`).
- **Решение: функция собирается заранее, Netlify получает готовый `.mjs`.**
  `vite build` в режиме SSR (`build.ssr: 'functions/api.ts'`,
  `ssr.noExternal: ['@eisenhower/core']`) вклеивает core в один файл
  `apps/api/dist/functions/api.mjs`; обычные npm-пакеты (`fractional-indexing`, позже
  `hono`, `zod`) остаются внешними, и NFT их трассирует как обычно. Каталог функций в
  `netlify.toml` — `apps/api/dist/functions`. `config.path` переживает сборку (Rolldown
  оставляет `export { config }`), маршрут бандлер видит. Спайк: собранная и упакованная
  функция отвечает `200` на `/api/health`.
- **Почему не сборка `packages/core` в `dist/`** (запасной план из issue): у core
  импорты без расширений, Node ESM их не резолвит — пришлось бы править каждый импорт
  core или добавлять бандлер в сам core. А `apps/web` потерял бы чтение core
  исходниками. Сборка приложения бандлером, который в репозитории уже есть, дешевле
  (человек, 2026-10-02).
- **Вклеивание core держит не одна строка конфига.** Связанный workspace-пакет Vite в
  SSR-сборке вклеивает и сам; `ssr.noExternal` указан явно, чтобы не зависеть от
  способа связывания. Проверено мутацией: с `rollupOptions.external` на
  `@eisenhower/*` тест `FUNCTION_IS_SELF_CONTAINED` падает.

### Разработка без `netlify dev` (человек, 2026-10-02)

- **`netlify dev` не используется, `netlify-cli` не ставится.** Он берёт функции из
  того же `dist/`, то есть требовал бы `vite build --watch`, и тянет 97 зависимостей.
- **У `apps/api` свой dev-сервер** (`npm run dev:api`, `127.0.0.1:8787`): Vite в
  режиме SSR загружает `src/app.ts` на каждый запрос — исходники и core читаются как
  есть, правка видна без пересборки. Запрос `node:http` переводит в `Request`
  `getRequestListener` из `@hono/node-server` — официального адаптера Hono для Node;
  пакет только в `devDependencies` и в функцию не попадает.
- **Один origin и в разработке:** `apps/web/vite.config.ts` проксирует `/api` на
  `127.0.0.1:8787`. CORS dev-сервера API выключен (`server.cors: false`), как на проде.
- **Что теряем и чем закрываем.** Локально не проверяются платформенные вещи: упаковка
  функции Netlify, маршрутизация по `config.path` (прокси Vite пускает в API и голый
  `/api`, Netlify — нет), правила `netlify.toml`, `Context` Netlify, лимиты рантайма.
  Упаковку держит тест `FUNCTION_IS_SELF_CONTAINED` по собранному файлу, платформу —
  критерий «после мержа прод отвечает на `/api/health`» (превью выключены, см.
  «Деплой только при мерже»). `Context` Netlify API не
  использует (`API_IGNORES_NETLIFY_CONTEXT`), поэтому dev-сервер ведёт себя как прод.
  Переменные окружения локально — из `.env`, а не с сайта Netlify.

### Деплой только при мерже (человек, 2026-10-03)

- **Превью PR и деплои веток выключены**, Netlify собирает только `production`.
  `netlify.toml`: `ignore = "exit 0"` в контекстах `deploy-preview` и `branch-deploy` —
  `@netlify/config` применяет `ignore` по контексту. Настройка живёт в репозитории, а не
  в UI сайта; в PR проверка Netlify отображается как пропущенная.
- **Цена:** платформу (упаковку функции, маршрут `config.path`) до мержа больше ничего
  не проверяет — первый настоящий запуск функции происходит на проде. До мержа остаётся
  тест `FUNCTION_IS_SELF_CONTAINED`, который собирает функцию и запускает её в Node.

## Скоуп

**In**

- `apps/api/functions/api.ts` — единственная функция, `export default (req) =>
  app.fetch(req)` и `export const config = { path: '/api/*' }`; приложение Hono в
  `apps/api/src/`.
- Сборка функции: `vite build` (SSR) с вклеенным `@eisenhower/core` в
  `apps/api/dist/functions/api.mjs`. Корневой `npm run build` собирает и её.
- Dev-сервер API (`npm run dev:api`) и прокси `/api` в `apps/web/vite.config.ts`.
- `netlify.toml`: `[functions] directory = "apps/api/dist/functions"`; превью PR и
  деплои веток выключены.
- `GET /api/health` — `200` и версия сборки. Ручка без входа, её же расширит #51.
- Разбор окружения через zod при старте: неизвестная или пустая обязательная переменная —
  явная ошибка с именем переменной, а не `undefined` в глубине кода.
- Логгер `apps/api` по правилам `CLAUDE.md` §9: четыре уровня, область обязательна,
  данные отдельным аргументом.
- Свой ESLint-конфиг `apps/api` поверх `eslint.config.base.js`: запрет `FunctionExpression`
  снимается (классы с методами), `typedef` на переменных остаётся. `PACKAGE_BOUNDARIES`
  из #48 распространяется на `apps/api` без правки правила.
- Правка `CLAUDE.md` §8: «только стрелочные функции» — для `apps/web` и `packages/core`;
  для `apps/api` — классы с методами, порядок членов public → private → static.

**Out**

- База, миграции, экран «Технические работы» — #51.
- Вход и сессии — #52.
- Ручки задач — #46.
- CORS: один origin, не нужен.
- `netlify dev` и `netlify-cli` — не используем (см. «Разработка без `netlify dev`»).
- Сборка `packages/core` в `dist/` — не делаем (см. «Результаты фазы 0»).

**Допущения**

- Функции Netlify на Node, не Edge (решение по стеку).
- Node на Netlify — 22 или новее (спайк гонялся на 22).

## Инварианты

- `ONE_ORIGIN`: фронт и API отдаются одним сайтом; ни одна ручка не отвечает
  CORS-заголовками.
- `ENV_FAILS_FAST`: приложение не обрабатывает ни одного запроса с неразобранным
  окружением.
- `API_HAS_NO_WEB_DEPS`: `apps/api` не импортирует `apps/web` (часть `PACKAGE_BOUNDARIES`).
- `API_IGNORES_NETLIFY_CONTEXT`: обработчик функции передаёт в приложение только
  `Request`; второй аргумент (`Context` Netlify) не используется — иначе dev-сервер
  вёл бы себя не как прод.
- `FUNCTION_IS_SELF_CONTAINED`: собранная функция не импортирует `@eisenhower/core` —
  core вклеен в `api.mjs`. Проверяется тестом по собранному файлу
  (`apps/api/tests/function-bundle.test.ts`): без этого сборка остаётся зелёной, а
  функция падает на первом запросе. Пока API core не импортирует, тест собирает тем же
  конфигом фикстуру, которая импортирует.
