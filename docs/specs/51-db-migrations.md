# #51 — База Postgres и миграции

## Задача

Подключить API к Postgres у Neon через Drizzle и применять миграции при холодном старте
функции — за интерфейсом, так что остальной код API не знает, чем и как мигрируется база.

## Прототип

Не требуется: пользователь ничего нового не видит. Экран «Технические работы» из
первой редакции задачи вынесен в #62 (см. «Решения»).

## Решения

Приняты человеком 2026-09-23 — 2026-09-28; пересмотрены после фазы 0 — 2026-10-03.

- **База — PostgreSQL у Neon.** SQLite невозможен: файловая система функции одноразовая.
  Neon подключается по HTTP или WebSocket, а не по TCP — соединения не копятся на
  стороне базы, пока функции рождаются и умирают.
- **ORM — Drizzle.** Схема на TypeScript, поэтому форма задачи не получает третьего
  описания рядом с типом `Task` и схемами zod. Миграции генерирует `drizzle-kit generate`,
  они лежат в git.
- **Рабочие запросы — драйвер `neon-http`**
  ([orm.drizzle.team/docs/connect-neon](https://orm.drizzle.team/docs/connect-neon)).
  HTTP быстрее для одиночных и неинтерактивных запросов; атомарность пачки даёт
  `db.batch([...])`. «Прочитать, потом записать» — два запроса без общей транзакции.
- **Окружение разбирается через `zod`** (человек, 2026-10-03). Это и `ENV_FAILS_FAST` из
  #50, который ждал согласования `zod`.

### Миграции при холодном старте (человек, 2026-10-03)

Первая редакция применяла миграции шагом после успешного деплоя прода, а пока они не
применены, API отвечал `503` и фронт показывал «Технические работы». Фаза 0 показала,
что так получается больше движущихся частей, чем нужно личному планировщику:

- шаг «после деплоя» — это локальный build-плагин Netlify с событием `onSuccess`
  (`@netlify/build@37.3.3`: `runsAfterDeploy`, падение не роняет деплой); плюс режим
  `503`, сравнение версий схемы и отдельный экран на фронте;
- без него код и схема всё равно расходятся на время между публикацией и миграцией.

Поэтому:

- **Функция сама приводит схему в актуальное состояние при холодном старте**, до того
  как обработает первый запрос. Пока миграция идёт, запрос ждёт. Тёплый инстанс второй
  раз не проверяет: «схема актуальна» — монотонный факт (схема только растёт, код
  инстанса не меняется), поэтому результат запоминается на время жизни инстанса.
- **Если миграция упала — бекенд падает с ошибкой.** Транзакция откатывается, запрос
  получает `500`, в лог — `log.error` с именем миграции. Следующий холодный старт или
  запрос пробует снова. Пользователь видит ошибку, а не «ведутся работы»; для одного
  пользователя без алертов это приемлемо. Понятный экран вместо ошибки — #62.
- **О сбое миграции сообщает сам API** (человек, 2026-10-03). Пока внешнего алерта нет,
  сбой должен быть виден без чтения логов функции:
  - `GET /api/health` → `500` `{"status":"migration_failed","migration":"<имя>"}` —
    проверяется одним `curl` или открытием адреса в браузере;
  - остальные ручки → `500` `{"error":"migration_failed"}` — отдельный код, а не общий
    `internal`, чтобы фронт (#62) мог отличить эту ошибку;
  - наружу уходит только имя миграции, без текста ошибки Postgres: он раскрывает схему.
    Полная ошибка — в `log.error`.
  - Имя миграции — тег из журнала drizzle (`0001_…`), а не номер: по нему сразу
    находится файл в `apps/api/drizzle/`.
  Настоящий алерт (письмо, Slack, телефон) — #63.
- **За интерфейсом** (человек, 2026-10-03). API зависит от абстракции «привести схему в
  актуальное состояние» (`SchemaMigrator`), а не от Drizzle и Neon: реализацию можно
  заменить (другой драйвер, другой migrator, шаг после деплоя), не трогая приложение.
  Drizzle и `@neondatabase/serverless` импортируются только в `apps/api/src/db/` —
  это держит линтер (`DB_BEHIND_INTERFACE`).
- **Миграция — через WebSocket-драйвер в транзакции, рабочие запросы — через HTTP.**
  Migrator drizzle для `neon-http` (`drizzle-orm@0.45.3`, `neon-http/migrator.js`)
  выполняет SQL по одному запросу без транзакции и пишет журнал только в конце: упавшая
  посередине миграция оставила бы схему наполовину применённой и без записи, а повтор
  упал бы на уже применённом DDL. Migrator WebSocket-драйвера (`drizzle-orm/neon-serverless`,
  тот же пакет `@neondatabase/serverless`) оборачивает прогон в одну транзакцию; DDL в
  Postgres транзакционен.
- **Параллельные холодные старты сериализуются `pg_advisory_lock`.** После деплоя может
  стартовать несколько инстансов сразу. Migrator drizzle читает «последнюю применённую»
  до своей транзакции, поэтому без блокировки второй инстанс повторил бы DDL. Блокировка
  берётся на выделенном соединении до вызова migrator и отпускается после.
- **SQL миграций едет в функцию.** Файлы `apps/api/drizzle/` попадают в собранный
  пакет функции; как именно (импорт в бандл или `included_files`) — решается в фазе 2.
- **У рантайм-роли API есть право на DDL.** Отдельная роль для миграций потеряла смысл
  вместе с отдельным шагом; для личного проекта это сознательная цена.
- **Локально — так же, как на проде.** `npm run dev:api` при первом запросе мигрирует
  dev-ветку Neon, отдельной ручной команды нет. Строка подключения — из `.env`.

### Проверка в разработке и в CI

- **Локальный стенд — Postgres 16 и локальный HTTP/WebSocket-прокси Neon в Docker.**
  Neon из окружения агента недоступен, а прокси позволяет прогнать настоящие драйверы
  `neon-http` и `neon-serverless`, а не подменять их `pg`. У человека — dev-ветка Neon.
- **Интеграционные тесты** (миграция на пустой базе, повтор, параллельный старт, падение)
  идут против базы, адрес которой задан в окружении теста. Без адреса они пропускаются с
  явным сообщением, а не молча. Подключить тот же стенд в CI (#57) сервисами
  `postgres` + прокси — часть фазы 2.

## Скоуп

**In**

- Разбор окружения через zod при старте (`ENV_FAILS_FAST`): `DATABASE_URL` и то, что
  появится дальше. Ошибка называет переменную.
- Интерфейс `SchemaMigrator` и реализация на Drizzle + `neon-serverless` с
  `pg_advisory_lock`; подключение для рабочих запросов через `neon-http`.
- Старт приложения: ни одна ручка не выполняется, пока миграция на этом инстансе не
  прошла успешно.
- `apps/api/src/db/schema.ts`, `drizzle.config.ts`, миграции в `apps/api/drizzle/`;
  первая миграция — служебная (таблиц предметной области ещё нет), её цель — провести
  конвейер от начала до конца.
- Правило линта `DB_BEHIND_INTERFACE`.
- Интеграционные тесты и стенд для них; сервисы в CI.

**Out**

- Таблицы пользователей и задач — #52 и #46.
- Режим «Технические работы», `503` и экран на фронте — #62 (человек, 2026-10-03).
- Шаг миграций после деплоя (build-плагин Netlify) — не делаем; интерфейс оставляет к
  нему дорогу.
- Откат миграций: не делаем; исправление — новой миграцией.
- Внешний алерт о неудачной миграции (письмо, Slack, телефон) — #63; здесь сбой
  сообщает сам API (см. «Решения»).
- Отдельная база под деплой-превью: превью выключены (#50).

**Допущения**

- Миграции небольшие и укладываются в первый запрос с запасом до лимита функции в 60 с.
- Код новой версии не обязан работать со старой схемой: до первого запроса нового
  инстанса схема догоняется.

## Инварианты

- `ENV_FAILS_FAST`: приложение не обрабатывает ни одного запроса с неразобранным
  окружением; ошибка называет переменную.
- `NO_WORK_ON_STALE_SCHEMA`: ни одна ручка не выполняется на инстансе, где миграция ещё
  не прошла успешно.
- `MIGRATION_IS_ATOMIC`: прогон миграций — одна транзакция; упавший прогон не оставляет
  ни частичной схемы, ни записи в журнале.
- `MIGRATION_IS_SERIALIZED`: параллельные старты не выполняют миграции одновременно;
  каждая миграция применяется ровно один раз.
- `MIGRATIONS_ARE_IDEMPOTENT`: старт на уже мигрированной базе не выполняет DDL и не
  меняет журнал.
- `MIGRATION_FAILURE_IS_REPORTED`: пока миграция не прошла, `/api/health` отвечает
  `500` с `status: migration_failed` и именем миграции, остальные ручки — `500` с
  `error: migration_failed`; текст ошибки базы в ответ не попадает.
- `DB_BEHIND_INTERFACE`: `drizzle-orm` и `@neondatabase/serverless` импортируются только
  в `apps/api/src/db/`; приложение зависит от интерфейсов.

## Критерии приёмки

- [x] Given не задан `DATABASE_URL` When запрос Then `500`, в логе — имя переменной.
- [ ] Given пустая база When первый запрос Then миграции применены, ответ `200`.
- [ ] Given мигрированная база When холодный старт Then DDL не выполняется, журнал
  миграций не изменился.
- [ ] Given два параллельных старта на пустой базе Then каждая миграция применена один
  раз, оба запроса — `200`.
- [ ] Given миграция с ошибкой When запрос Then `500` `{"error":"migration_failed"}`,
  схема и журнал как до прогона, `log.error` с именем миграции и ошибкой базы; Given
  ошибку исправили When следующий старт Then миграция применена.
- [ ] Given миграция с ошибкой When `GET /api/health` Then `500`
  `{"status":"migration_failed","migration":"<тег>"}`, текста ошибки базы в теле нет.
- [ ] Given тёплый инстанс When второй запрос Then к журналу миграций не обращается.
- [ ] Given импорт `drizzle-orm` вне `apps/api/src/db/` Then lint красный.
- [ ] Given `npm run dev:api` на пустой dev-базе When первый запрос Then база мигрирована.
- [ ] Given прод-деплой с новой миграцией When первый запрос Then миграция применена,
  `/api/health` — `200`.
