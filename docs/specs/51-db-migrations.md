# #51 — База Postgres и миграции

## Задача

Подключить API к Postgres у Neon через Drizzle и применять миграции один раз на деплой —
шагом сборки, а не в функции: файлы миграций и migrator в функцию не попадают.

## Прототип

Не требуется: пользователь ничего нового не видит. Экран «Технические работы» из
первой редакции задачи вынесен в #62 (см. «Решения»).

## Решения

Приняты человеком 2026-09-23 — 2026-09-28; пересмотрены после фазы 0 и ещё раз в начале
фазы 2 — 2026-10-03.

- **База — PostgreSQL у Neon.** SQLite невозможен: файловая система функции одноразовая.
  Neon подключается по HTTP или WebSocket, а не по TCP — соединения не копятся на
  стороне базы, пока функции рождаются и умирают.
- **ORM — Drizzle.** Схема на TypeScript, поэтому форма задачи не получает третьего
  описания рядом с типом `Task` и схемами zod. Миграции генерирует `drizzle-kit generate`,
  они лежат в git.
- **Рабочие запросы — драйвер `neon-http`**
  ([orm.drizzle.team/docs/connect-neon](https://orm.drizzle.team/docs/connect-neon)).
  HTTP быстрее для одиночных и неинтерактивных запросов; атомарность пачки даёт
  `db.batch([...])`. «Прочитать, потом записать» — два запроса без общей транзакции.
- **Окружение разбирается через `zod`** (человек, 2026-10-03). Это и `ENV_FAILS_FAST` из
  #50, который ждал согласования `zod`.

### Миграции — шагом сборки, один раз на деплой (человек, 2026-10-03)

История решения. Первая редакция применяла миграции шагом после успешного деплоя
(build-плагин Netlify, `onSuccess`) и держала режим `503`. Вторая — при холодном старте
функции. В начале фазы 2 выяснилось, чего стоит вторая:

- публичный `migrate()` drizzle читает миграции с диска (`drizzle-orm@0.45.3`,
  `migrator.js`), значит SQL пришлось бы вклеивать в бандл функции и вызывать
  внутренний API drizzle (`db.dialect.migrate`, помечен `@internal`);
- migrator не сообщает, какая миграция упала, а API должен был отдавать её тег;
- каждый холодный старт открывал бы WebSocket и шёл в журнал миграций.

Человек (2026-10-03): «миграции срабатывают один раз», файлы миграций в сборку сервера
не едут. Поэтому:

- **Миграции применяет скрипт `npm run db:migrate`, и на проде его запускает сборка
  Netlify:** `command = "npm run build && npm run db:migrate"` в контексте `production`
  (`netlify.toml`). Сначала сборка, потом
  миграция: упала сборка — база не тронута; упала миграция — команда завершается с
  ошибкой, деплой не публикуется, на проде остаётся старый код. Превью и деплои веток
  выключены (#50), так что скрипт запускает только прод-деплой.
- **«Один раз» держат две вещи:** скрипт вызывается один раз на деплой, а журнал
  drizzle (`drizzle.__drizzle_migrations`) пропускает уже применённое.
- **Скрипт — публичный `migrate()` из `drizzle-orm/neon-serverless`** с папкой
  `apps/api/drizzle/`. WebSocket-драйвер, а не HTTP: migrator `neon-http` выполняет SQL
  по одному запросу без транзакции и пишет журнал только в конце — упавшая посередине
  миграция оставила бы схему наполовину применённой. Migrator WebSocket-драйвера
  оборачивает прогон в одну транзакцию (`pg-core/dialect.js`); DDL в Postgres
  транзакционен.
- **Параллельные прогоны сериализуются `pg_advisory_lock`.** Migrator читает «последнюю
  применённую» до своей транзакции, поэтому без блокировки второй прогон повторил бы
  DDL. Блокировка берётся на том же соединении до вызова migrator и отпускается после.
  Гарантирует ли Netlify, что сборки одного сайта не идут одновременно, не проверялось —
  блокировка от этого не зависит и защищает также ручной запуск во время деплоя.
- **Блокировку прогон ждёт не дольше минуты** (`lock_timeout`). Иначе зависшая чужая
  сессия держала бы сборку до её таймаута молча.
- **Миграциям нужен прямой адрес базы.** За pooled-адресом Neon (`-pooler` в хосте)
  стоит PgBouncer в режиме транзакций, сессионная блокировка там не привязана к клиенту;
  такой `DATABASE_URL` скрипт отклоняет с понятной ошибкой. Поведение блокировки за
  pooler не проверялось — решение принято по известному ограничению PgBouncer.
- **Прогон сверяет папку с журналом.** Migrator drizzle применяет только миграции новее
  последней записи журнала и не сверяет содержимое (`pg-core/dialect.js`): миграция с
  меткой времени старше применённой (ветка смержена позже) или правка применённого
  файла пропускались бы молча при зелёной сборке. После `migrate()` скрипт проверяет,
  что каждая миграция из папки есть в журнале с тем же хешем, иначе падает. Следствие:
  применённая миграция неизменяема.
- **Скрипт запускается через Vite** (`apps/api/scripts/migrate.js` загружает
  `src/migrate.ts` тем же `ssrLoadModule`, что и dev-сервер): TypeScript без
  дополнительного раннера в зависимостях, а окружение — из `apps/api/.env`, как у
  `npm run dev:api`.
- **В функции нет ни миграций, ни migrator** (`MIGRATIONS_STAY_OUT_OF_FUNCTION`). В
  рантайме остаются `schema.ts` и подключение `neon-http`.
- **О сбое миграции сообщает упавший деплой.** Полная ошибка Postgres — в логе сборки,
  он приватный. Ответы `migration_failed` в API больше не нужны. Какая именно миграция
  упала, drizzle не называет; в логе — текст ошибки базы, по нему находится файл.
  Настоящий алерт (письмо, Slack, телефон) — #63.
- **`/api/health` проверяет базу.** Ручка читает служебную таблицу через `neon-http`:
  `200`, если база доступна и схема применена; `500`
  `{"status":"database_unavailable","version":"<коммит>"}`, если нет. Текст ошибки базы
  в ответ не попадает — он в `log.error`. Так после деплоя одним `curl` видно, что
  миграция доехала и функция достаёт до базы. Ответа базы ручка ждёт не дольше 10 с:
  зависшая база — тоже `database_unavailable`, а не таймаут платформы.
- **Успешная проверка базы запоминается на минуту** (человек, 2026-10-03: «не гонять
  впустую трафик к базе»). Пока срок не вышел, `/api/health` на тёплом инстансе в базу не
  ходит. Сбой не запоминается: он перепроверяется на каждом запросе, и возвращение базы
  видно сразу. Цена: о сбое базы ручка узнаёт с опозданием до минуты. Это осознанное
  исключение из правила #50 «состояние в памяти функции не держим»: память пропадает
  вместе с инстансом, и холодный старт проверяет базу заново.
- **За интерфейсом** (человек, 2026-10-03). Код вне `apps/api/src/db/` зависит от
  интерфейсов (`SchemaMigrator`, `DatabaseProbe`), а не от Drizzle и Neon: реализацию
  можно заменить, не трогая приложение. `drizzle-orm` и `@neondatabase/serverless`
  импортируются только в `apps/api/src/db/` — это держит линтер (`DB_BEHIND_INTERFACE`).
- **Первая миграция — служебная:** таблица `app_meta` (ключ — значение). Таблиц
  предметной области ещё нет, её цель — провести конвейер от `drizzle-kit generate` до
  чтения из функции.
- **Версия Node сборки закреплена:** `NODE_VERSION = "22"` в `netlify.toml`. Скрипту
  нужен глобальный `WebSocket`, он есть с Node 22.
- **Локально миграции — командой.** `npm run db:migrate` мигрирует базу из
  `apps/api/.env` (dev-ветка Neon или стенд). `npm run build` и `npm run dev:api` базу
  не трогают.

### Принятые риски (человек, 2026-10-03)

- **Схема меняется раньше кода.** Между миграцией и публикацией деплоя старый код
  работает на новой схеме. Миграции обязаны быть совместимы со старым кодом:
  добавлять, а не ломать. Ломающее изменение — двумя деплоями.
- **Откат деплоя схему не откатывает.** Откатов миграций нет; исправление — новой
  миграцией.
- **У сборки есть доступ к прод-базе.** `DATABASE_URL` доступна и сборке, и функции
  (в Netlify переменная по умолчанию идёт во все scope). Роль одна, с правом на DDL;
  отдельная роль без DDL для рантайма — не в этой задаче.

### Проверка в разработке и в CI

- **Локальный стенд — Postgres 16 и прокси Neon в Docker**
  (`apps/api/stand/docker-compose.yml`): `postgres:16` и
  `ghcr.io/timowilhelm/local-neon-http-proxy` (человек, 2026-10-03). Прокси говорит по
  HTTP и WebSocket, поэтому драйверы `neon-http` и `neon-serverless` работают настоящие,
  а не подменяются `pg`. Адрес стенда — `db.localtest.me`; по этому имени код в
  `src/db/` направляет драйвер на порт прокси без TLS. У человека — dev-ветка Neon.
- **Интеграционные тесты** (миграция на пустой базе, повтор, параллельный прогон,
  падение, проверка базы) идут против базы из `TEST_DATABASE_URL`. Без переменной они
  пропускаются с явным сообщением, а не молча. CI (#57) поднимает стенд тем же
  compose-файлом, что и разработчик (`docker compose up -d --wait`), а не сервисами
  GitHub Actions: прокси при старте пишет в базу и должен дождаться её готовности, а
  сервисы друг друга не ждут.
- **Образ прокси закреплён дайджестом**, а не тегом `main`: образ сторонний, тег можно
  перезаписать.

## Инварианты

- `ENV_FAILS_FAST`: приложение не обрабатывает ни одного запроса с неразобранным
  окружением; ошибка называет переменную.
- `MIGRATIONS_STAY_OUT_OF_FUNCTION`: в собранной функции нет ни SQL миграций, ни
  migrator, ни драйвера `neon-serverless` drizzle.
- `MIGRATION_IS_ATOMIC`: прогон миграций — одна транзакция; упавший прогон не оставляет
  ни частичной схемы, ни записи в журнале.
- `MIGRATION_IS_SERIALIZED`: параллельные прогоны не выполняют миграции одновременно;
  каждая миграция применяется ровно один раз.
- `MIGRATIONS_ARE_IDEMPOTENT`: прогон на уже мигрированной базе не меняет ни схему, ни
  журнал.
- `NO_MIGRATION_IS_SKIPPED`: успешный прогон означает, что каждая миграция из папки
  есть в журнале с тем же хешем; иначе прогон падает.
- `FAILED_MIGRATION_FAILS_BUILD`: скрипт миграций при любой ошибке завершается с
  ненулевым кодом; в `netlify.toml` он стоит в команде сборки контекста `production`
  после `npm run build`.
- `DATABASE_FAILURE_IS_REPORTED`: если база недоступна или схема не применена,
  `/api/health` отвечает `500` со `status: database_unavailable`; текст ошибки базы в
  ответ не попадает.
- `DATABASE_CHECK_IS_CACHED`: после успешной проверки тёплый инстанс минуту не ходит в
  базу ради `/api/health`; сбой не запоминается.
- `DB_BEHIND_INTERFACE`: `drizzle-orm` и `@neondatabase/serverless` в коде приложения
  (`src/`, `functions/`) импортируются только в `apps/api/src/db/`.
