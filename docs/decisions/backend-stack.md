# Решение: стек бекенда для синхронизации задач

Статус: стек, аутентификация, отказ от офлайна, монорепозиторий, DTO и драйвер выбраны.
Открыты четыре пункта в конце файла — они блокируют спеку, но не первую фазу.
Дата: 2026-09-23, правки 2026-09-24.

Задача, которая это вызвала: задачи должны синхронизироваться между телефоном и
компьютером. В MVP синхронизация была вне скоупа (`docs/specs/4-architecture.md:37`),
поэтому это новая работа.

Issue:

- [#46](https://github.com/shhhwepsss/eisenhower-todo/issues/46) — синхронизация задач,
  основная задача. Скоуп, инварианты, критерии приёмки и шесть фаз живут там.
- [#45](https://github.com/shhhwepsss/eisenhower-todo/issues/45) — явный признак
  изменения в мутациях домена. Отдельная задача, к синхронизации отношения не имеет.

Спека появится в `docs/specs/46-sync-backend.md`, когда закроются открытые вопросы.

## Принято

### Хостинг — Netlify

Фронт уже собирается в статику (`vite build`, `package.json:8`), поэтому сайт и API
живут в одном проекте Netlify. Следствие, ради которого это и выбрано: один origin,
значит CORS не нужен, а cookie-авторизация работает без обходных путей.

### Рантайм — Netlify Functions на Node, не Edge Functions

Обработчик Netlify Functions принимает стандартные `Request`/`Response`
([docs.netlify.com/build/functions/api](https://docs.netlify.com/build/functions/api)).
У Hono `app.fetch` имеет ровно такую сигнатуру, поэтому адаптер не нужен — приложение
подключается напрямую.

Edge Functions отклонены сознательно. Официальный путь Hono для Netlify — именно они
(`import { handle } from 'jsr:@hono/hono/netlify'`,
[hono.dev/docs/getting-started/netlify](https://hono.dev/docs/getting-started/netlify)),
но это Deno и импорты через `jsr:`, что усложняет работу с npm-пакетами и драйверами
базы. Выигрыш в задержке для личного планировщика не нужен.

### Фреймворк — Hono

Выбран человеком. Fastify и NestJS решают ту же задачу и поэтому не рассматриваются:
берётся что-то одно.

### Валидация — zod на обоих слоях

Одна библиотека и для входных данных HTTP, и для бизнес-правил. `class-validator`
рядом с zod означал бы, что форма `Task` описана дважды, а это рассинхрон по
построению — то же нарушение SSOT, которое ловится на ревью (`CLAUDE.md` §8).

Схемы zod пригодны к повторному использованию на фронте, в декодере снапшота
(`src/storage/decode.ts`).

### База — PostgreSQL у Neon

Выбрано человеком. SQLite в любом случае был невозможен: файловая система функции
одноразовая (см. ниже).

Neon подключается не по TCP, а по HTTP или WebSocket — ровно то, что нужно функции,
которая умирает после ответа. У Drizzle для этого есть готовые драйверы `neon-http`
и `neon-websockets`, под капотом оба используют пакет `@neondatabase/serverless`
([orm.drizzle.team/docs/connect-neon](https://orm.drizzle.team/docs/connect-neon)).

**Драйвер — `neon-http`.** Решено человеком. По документации Drizzle HTTP быстрее для
одиночных и неинтерактивных запросов, а WebSocket нужен только для интерактивных
транзакций и совместимости с драйвером `pg`.

Чего нам достаточно и почему: атомарность пачки даёт `db.batch([...])` — список
запросов отправляется одним пакетом
([orm.drizzle.team/docs/batch-api](https://orm.drizzle.team/docs/batch-api)), условие
одно — список известен заранее. Сценарий «прочитать, потом записать» делается двумя
запросами, сознательно **без общей транзакции**.

Записанное следствие: если когда-нибудь понадобится транзакция, внутри которой решение
принимает наш код между запросами, потребуется переход на `neon-websockets`. Это смена
драйвера, а не переписывание запросов.

### ORM — Drizzle

Выбрано человеком (решение вернулось к Drizzle после короткого захода на Prisma).

Схема описывается на TypeScript, поэтому форма задачи не порождает третьего описания
рядом с типом `Task` (`src/domain/types/task.ts`) и схемами zod. Миграции генерируются
через `drizzle-kit generate` и применяются `drizzle-kit migrate`
([orm.drizzle.team](https://orm.drizzle.team/docs/connect-neon)); когда именно они
применяются при деплое на Netlify — вопрос спеки, автоматически это не происходит.

## Что serverless меняет в требованиях

Это не детали реализации, а ограничения, из которых придётся исходить в спеке.

- **Процесс не живёт между запросами.** Ни кеш, ни состояние синхронизации нельзя
  держать в памяти.
- **Файловая система одноразовая.** SQLite на диске невозможен, база только внешняя.
- **Пул соединений к Postgres не переживает вызов.** Поэтому и взят Neon: подключение
  идёт по HTTP или WebSocket, а не по TCP, и соединения не накапливаются на стороне
  базы после смерти процесса.
- **Синхронная функция ограничена 60 секундами**
  ([docs.netlify.com/build/functions/configuration](https://docs.netlify.com/build/functions/configuration)).
  С запасом достаточно, но полная выгрузка задач не должна упираться в этот предел.

## Аутентификация — вход через Google

Решено человеком: полноценный логин, единственный провайдер — Google. Общий секретный
токен рассматривался и отклонён.

Следствия, которые нужно держать в голове при проектировании:

- В базе появляются пользователи, и у каждой задачи есть владелец. Выборка задач без
  фильтра по владельцу становится дырой в доступе, а не просто ошибкой — это кандидат
  в именованные инварианты спеки.
- Сессия живёт в cookie. Поскольку фронт и API на одном origin (см. решение про
  Netlify), хватает `HttpOnly` + `Secure` + `SameSite=Lax`, без возни с межсайтовыми
  cookie.
- Готовый путь для Hono — Auth.js через `@hono/auth-js`, с адаптером Drizzle и
  провайдером Google; в примере из документации Hono сессия там `strategy: 'jwt'`
  ([hono.dev, пример с Auth.js](https://github.com/honojs/website/blob/main/examples/hono-authjs.md)).
  JWT-сессия для serverless удобна тем, что проверка запроса не идёт в базу.
  Альтернативы из того же списка — Better Auth и минимальный `@hono/oauth-providers`.
  Выбор между ними — отдельное решение, потому что это зависимость (`CLAUDE.md` §10)
  и лишние таблицы в схеме.

## Офлайн — не делаем

Решено человеком: источник правды — база на сервере. Без сети приложение не работает,
офлайн-режима и очереди изменений в этой задаче нет.

Цена названа заранее: экран ошибки станет появляться чаще, чем сейчас, потому что сеть
отваливается охотнее, чем `localStorage` (нынешнее поведение при недоступном хранилище —
`docs/specs/4-architecture.md:348`). Кеш на чтение рассматривался и отложен; если
решение изменится, оно меняет роль `src/storage`, а не только серверную часть.

## Структура — монорепозиторий

Решено человеком. `src/domain` вместе со схемами zod переезжает в общий пакет, чтобы
форма задачи была описана один раз на фронт и бек.

Деплой от этого не усложняется: фронт и функции остаются одним сайтом Netlify и уезжают
одним деплоем. Netlify умеет и раздельные сборки из монорепозитория через base/package
directory ([docs.netlify.com/build/configure-builds/monorepos](https://docs.netlify.com/build/configure-builds/monorepos)),
но это понадобится только если бек когда-нибудь переедет на другой сервис. Тогда же
появятся и настоящие издержки: неатомарные деплои (API обязан переживать старого
клиента) и CORS.

Раскладка согласована с человеком после разбора у `system-architect`:

```
eisenhower-todo/
  package.json          # workspaces: ["apps/*","packages/*"], только скрипты-оркестраторы
  netlify.toml          # publish = apps/web/dist, functions = apps/api/functions
  tsconfig.base.json
  packages/core/        # @eisenhower/core: переезд src/domain/ целиком + zod-схемы + контракты ручек
  apps/web/             # нынешний src/{state,storage,ui,shared}, vite.config.ts, index.html
  apps/api/
    functions/api.ts    # единственная функция: export default (req) => app.fetch(req)
    src/{routes,services,auth,db}/
    drizzle/            # сгенерированные миграции, в git
```

Решения внутри раскладки:

- **Схема Drizzle живёт в `apps/api/src/db/schema.ts`, не в общем пакете.** Общее — форма
  `Task` и схемы zod, а не форма строки в базе. Иначе `drizzle-orm` попадает в браузерный
  бандл ради типов.
- **Алиас `@/` остаётся, но пер-приложением.** Внутри `apps/web` исчезает только
  `@/domain`, он становится `@eisenhower/core`: 54 импорта в `src` и 40 в `tests`,
  механическая замена. Сам `src/domain/` при переезде не правится — он ни на что по
  алиасу не ссылается.
- **React Compiler не затрагивается:** он включён внутри `vite.config.ts:8-11`, файл
  уезжает в `apps/web` целиком, и тесты берут тот же конфиг.
- **У `apps/api` свой ESLint-конфиг** (решено человеком), а не общий с фронтом. Стилевые
  правила в нём свои; какие именно из фронтовых переезжают — решается при создании
  конфига, а не заранее.

Риск переезда, который обязан быть в скоупе фазы: globs в `eslint.config.js:68` и
`:91-93` захардкожены на `src/`, а `tests/layer-boundaries.test.ts:9,70` прогоняет
ESLint по этим путям. Если не обновить их вместе с переездом, машинные проверки границ
слоёв выключатся бесшумно, и `npm run lint` останется зелёным.

## DTO на всех границах

Решено человеком: DTO и маппер стоят на каждой границе — контроллер, use-case, сущность,
база. Совет `system-architect` был обратным (схлопнуть до двух представлений, потому что
`Task` уже сериализуемая форма — `src/domain/types/task.ts:4,25-30`), и человек его
отклонил осознанно.

Цена решения, записанная заранее: новое поле задачи добавляется примерно в семи местах
вместо двух. Смягчающее обстоятельство: при точно типизированных мапперах забытое поле
ловится компилятором, то есть это объём работы, а не тихая поломка.

## Явный признак изменения вместо сравнения по ссылке — отдельная задача

Сейчас «ничего не изменилось» определяется по идентичности ссылки: мутация возвращает
тот же объект (`src/domain/mutations.ts:38`), редьюсер сравнивает `next === current`
(`src/state/reducer.ts:51`). Человек признал контракт опасным: он держится только
дисциплиной всех мутаций.

Решено: мутации будут возвращать явный признак изменения вместе с задачей, **но это
отдельная задача со своим issue** и инвариантом `BEHAVIOR_PRESERVED` — она затрагивает
все мутации, редьюсер и их тесты, и к синхронизации отношения не имеет.

Одно сравнение по ссылке останется и убрать его нельзя: `src/state/AppStateProvider.tsx:68`
гасит лишнюю запись в хранилище, опираясь на то, что `useReducer` возвращает тот же
объект состояния. Это механика React, а не наш контракт.

## Не решено — блокирует спеку

Те же четыре пункта перечислены в issue #46. Решать их молчанием нельзя.

1. **Библиотека аутентификации.** Auth.js через `@hono/auth-js` (готовый пример с
   адаптером Drizzle и провайдером Google есть в документации Hono), Better Auth или
   сборка руками на `@hono/oauth-providers`. Разница — в количестве таблиц, которые
   библиотека навязывает схеме, и в объёме кода, который придётся писать самим.
2. **Стиль сущностей на беке.** У `apps/api` свой ESLint-конфиг, поэтому запрет методов
   класса (`eslint.config.js:62`, селектор `FunctionExpression`) там не действует
   автоматически. Классы-сущности с методами или модули стрелочных функций, принимающих
   зависимости параметрами. Фабрики, возвращающие объект со стрелками, отклонены.
3. **Кто ставит `updatedAt`** после появления сервера. Сейчас это делает только `touch`
   на клиенте (`src/domain/mutations.ts:30-35`), инвариант `TIMESTAMPS_MONOTONIC_PER_TASK`.
   Слияние двух устройств опирается ровно на это поле, поэтому `DEFAULT now()` в базе
   одновременно с клиентским `touch` — гарантированный рассинхрон.
4. **Тип колонок времени.** Декодер требует ровно три знака миллисекунд
   (`src/storage/guards.ts:27`), а `timestamptz` в Postgres имеет микросекундную точность.
   Либо `timestamptz` плюс маппер, обязанный звать `toISOString()`, либо `text`. В любом
   случае нужен round-trip тест `Task` → строка → `Task`.

## Решено по ходу обсуждения

- **Задачи из `localStorage` переносятся на сервер** при первом входе через Google.
  Требование идемпотентности: повторный вход не плодит дубли, у задач есть `id`.
- **`UiSettings` не синхронизируются** — тема и сортировка остаются предпочтением
  устройства (отдельный порт, `src/storage/types/repository.ts:28-31`).
- **`STORAGE_WRITE_IS_ATOMIC` в форме «единица записи — снапшот целиком» отменяется**
  (`src/storage/types/repository.ts:17-21`, там написано «отдельного `save(task)` нет и
  не будет»). Порт получает запись по задаче, атомарность переезжает на базу. Это правка
  спеки §4, её надо внести письменно, а не «решить внутри адаптера».
- **Новый инвариант `TASKS_ARE_OWNER_SCOPED`** — ни один запрос к задачам не собирается
  без фильтра по владельцу.

## Что уже готово в коде к синхронизации

- У задачи есть `updatedAt` и надгробие `deletedAt` (`src/domain/types/task.ts:28-30`),
  признаки лежат плоско «под будущее слияние по полям» (`src/domain/types/task.ts:6-7`).
- Порты хранилища уже асинхронные и объявлены заменяемыми
  (`src/storage/types/repository.ts:38-40`).

Что не готово: единица записи — снапшот целиком, `saveAll`
(`src/storage/types/repository.ts:52`). Для сервера так нельзя: телефон затрёт
изменения компьютера. Нужна запись по задаче.

Отдельный риск для спеки: порядок задаётся дробным индексом `rank`
(`src/domain/types/task.ts:24`), и две задачи, созданные на разных устройствах
независимо, могут получить одинаковый `rank`. Сортировке понадобится устойчивый
доводчик, например `id`.
